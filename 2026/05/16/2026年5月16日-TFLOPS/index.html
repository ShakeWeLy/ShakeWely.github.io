1 TFLOPS

“12.7 TFLOPS” ≈ 每秒 12.7 万亿次浮点运算

Tensor Core（AI训练常用）：

  • FP16 / Tensor TFLOPS：约 50~100+ TFLOPS（视稀疏性和模式）

在 3060 上：

情况 FPS

AI 里真正速度还取决于：

  • CUDA 核心利用率
  • 显存带宽（3060 是 192-bit）
  • Tensor Core 是否启用（混合精度

FPS≈模型计算量GPU算力

例如：

  • GPU：12 TFLOPS
  • 模型：120 GFLOPs/帧

那么理论：

FPS≈12×1012120×109=100FPS\approx\frac{12\times10{12}}{120\times10{9}}=100FPS≈120×10912×1012=100

理论上约：

  • 100 FPS

FLOPs ≠ 实际速度

有些模型：

  • FLOPs 很低
  • 但 FPS 不高

因为：

  • 内存访问特别碎
  • depthwise conv 很多
  • 小 kernel 太多
  • GPU 利用率低

例如：

模型 FLOPs低 但速度
MobileNet ✅ 不一定快
EfficientNet ✅ 经常偏慢
YOLO FLOPs不算低 但非常快

推理时间真正近似公式

更接近：

推理时间= 计算时间 + 显存访问时间 + 调度开销 + 数据传输时间推理时间

Params（参数量）

问题分析

结论可以分三块说：你们在比的不是同一个计时范围、拍照路径和执行线程和视频不一样、前几帧变慢是正常现象。

1. 为什么 [AI_INFERENCE_SINGLE] 比 Ultralytics 的 Speed: 大很多？

[AI_INFERENCE_SINGLE] 包的是整段 process_frame + _apply_fps_overlay，而日志里 Ultralytics 的
Speed: … preprocess … inference … postprocess 一般指 model(...)（predict）内部拆的三段。

以 FruitInAreaFrameProcessor 为例，YOLO 打完成绩之后你还有一大段工作在同一次计时里：

你日志里是 480x640、多类、十多颗水果，分割模型在 results[0].plot() 里要把每个实例的 mask 叠到图上，多半是纯 CPU/OpenCV，很容易比 predict 本身的几十毫秒再长出一大截。所以 889ms vs 里外合计约 129ms：差的主要是「YOLO predict 之外的 plot/画框/叠加」，而不是表格里那一行 inference 变慢了。

外层还有 start_processing_single_frame 里对 _apply_fps_overlay（若 settings.ai_draw_fps 为真则会 copy + addWeighted）等，也都在同一计时窗里。

2. 为什么「拍照多帧检测」和视频流里看到的延迟感觉差很多？

拍照路径：stream_process_multiple_frames 里每一帧都是**「新建一个线程池 → 扔一次 start_processing_single_frame → shutdown**」：

你贴的日志里也印证了这一点：第 1/2/3 帧分别是 ThreadPoolExecutor-0_0、-1_0、-2_0，也就是每轮都是不同的 worker 上下文。再配合上面说的「predict 只占一部分」以及首帧预处理在 Ultralytics 里也会偏高（见你第一帧 preprocess 25.8ms vs 后面的 ~0.9ms），体感就会和「稳定在 ~14ms inference」的那段视频日志差很远。

视频连续检测：走的是 start_processing 的那种长期循环，同一条链路反复跑，model/plot/cuDNN/缓存都更容易进入稳态；你在 test_120fps.mp4 那一段里看到的 ~13–16ms inference，就是这类稳态。

  1. 不要使用三个线程

3. 为什么视频前几帧也很大、后面突然变小？

这和你日志里的曲线一致：第 1 帧 ~92ms → 中间的 ~43–46ms → 再往后的 ~13–16ms。常见原因包括：

  • CUDA / cuDNN 首轮选算法、建缓存、allocator 铺开；
  • Ultralytics 内部预处理/后处理在第一两次路径上会触发的初始化（你已有「首帧 preprocess 明显更高」的现象）；
  • 若当时是刚拉起读流/刚切源，还有可能叠上 解码/缓冲区尚未稳定。

所以「前几张大、后面稳定在十几毫秒」是预期行为，不是问题特有的异常。

若要验证：在同一个 process_frame 里用 time.perf_counter() 分别包住 model(...)、plot()、draw_area，你会很快看到_gap 主要是在哪一段；结构上也可以考虑拍照路径不要每帧新开 ThreadPoolExecutor（复用线程池或直接在当前线程推理），能减少线程与调度带来的不确定性。

指标 情况

plot ≈5 ms

说明：这轮请求时 GPU/CUDA 已经热好，首帧没有再出现 model≈1248 ms；差异主要来自整条 process_frame 里 model(...)，不是 plot/draw_area。

2）本地视频、ProcessorThreadWebcam（约 21:11:46）

帧序 Ultralytics inference model= 墙钟 plot
第 1 帧 94.8 ms 102 ms 12.9 ms
之后几帧 ～13～20 ms ～24～29 ms ～5～12 ms
  • warmup：第 1 帧 GPU/CUDA、cudnn、缓存等最重，和你们之前「视频前几帧慢」一致。
  • 为什么 model= 常比 Ultralytics 的 inference 再高 ~10 ms？
    perf_counter 包住的是整段 model(...) 返回：里面除了「纯 kernel 推理」，往往还有同步、解码型后处理等在 Python/C++ 边界上的墙钟开销；Ultralytics 打在日志里的那一段 不见得等于你在 Python 侧量的整段耗时，所以会看到 Ultra ~14–20 ms、你却量到 ~23–29 ms，这是正常现象。
  • plot 仍会占几毫秒～十几毫秒，仍远小于 model。

3）两段合在一起说明什么？

  • 同一次进程里：若先有「冷线程 / 首次 CUDA」路径，会出现 model 一秒钟级 spike（你更早那次的 1248 ms）；同一进程稍后再在 ThreadPoolExecutor 里跑，model 就只 ～90 ms。
    本质是 谁在什么线程上、第几次碰 GPU，不是 plot。
  • 固定 ProcessorThreadWebcam 线程持续跑：首帧大一点，后面 model 明显低于拍照路径里重复的 ~80 ms，是因为 Ultralytics 内部计时和你们外层墙钟口径不同 + 流水线是否持续喂帧；你这两段里都说明 瓶颈仍在 model(...)。

若要压掉拍照首帧 ~1 s：在应用启动或首次检测前，在同一个最终用于推理的线程上做一次 warmup，或 stream_process_multiple_frames 里复用单个 ThreadPoolExecutor/ProcessPoolExecutor，避免每次都是「从未跑过 CUDA 的工作线程」。需要的话可以再改 detector 那一段具体代码方案。
