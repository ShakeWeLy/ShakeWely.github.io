2026年6月9日 训练后量化

最近在搞量化相关的, 之前学习到的量化也只是皮毛. 什么是量化? 怎么量化?

这篇用于深入理解和使用量化, 并进行结果分析

1 前言

1.1 量化

量化分为训练后量化(PTQ)和训练时量化(QAT)

PTQ 主要是针对模型压缩后,比如int8, 带来的精度损失进行微调. 具体流程是找出最合适的 Scale（缩放因子），把 FP32 的浮点数安全地映射到 INT8 的整数范围（−128-128−128 到 127127127）。用极少量的校准数据, 提高统计学方法挽回精度的损失.

QAT 主要是对量化后得模型进行微调,找出最合适的 Scale（缩放因子）, 相当于预训练模型微调训练

量化的本质就是寻找最优映射（Scale）并尽可能减少信息损失：

  • PTQ： 考前不复习，直接用统计学公式盲猜一个最优鞋码（Scale），几分钟搞定。
  • QAT： 穿上鞋去操场上拉练几个大项（跑梯度下降训练），让鞋码（Scale）和脚（Weights）磨合到最完美的契合度。

但 QAT 比 PTQ 还多做了一件事：对抗“舍入误差”（Rounding Error）。

把浮点数变成整数，不可避免地要进行四舍五入。

  • PTQ 极其死板： 0.4 必须变 0，0.6 必须变 1。
  • QAT 极其聪明： 通过神经网络训练，模型可能会发现，在当前这一层，把 0.4 强制变成 1 反而能让后面的矩阵乘法结果更接近原版。这种“不讲理”的微调能力，是纯统计学的 PTQ 绝对做不到的。

2 PQT

2.1 具体流程

普通 PTQ 的目标是找出最合适的 Scale（缩放因子），把 FP32 的浮点数安全地映射到 INT8 的整数范围（−128-128−128 到 127127127）。它的具体步骤如下：

1. 权重（Weights）直接量化

模型的权重（比如卷积层、全连接层的参数）是固定的、静态的。

  • 工具（如 TensorRT 或 ModelOpt）会直接扫描每一层权重的最大值（Max）和最小值（Min）。
  • 映射公式非常直接：把这个最大绝对值直接映射到 INT8 的 127127127。
  • 耗时： 几秒钟，纯粹的矩阵运算。

2. 激活值（Activations）校准（Calibration）

这是普通 PTQ 最关键的一步。网络的输入和中间层的输出（激活值）是动态的，输入不同的图片或文本，中间层的数值范围大不相同。

  • 准备校准集： 抽取极少量的真实数据（通常 32 ~ 128 个样本，不需要标签）。
  • 前向跑数据（Forward Pass）： 让这些数据在 FP32 模型里跑一次，工具会像“监控摄像头”一样，记录下每一层激活值数据的分布直方图。
  • 计算激活值 Scale： 因为激活值可能存在极端的离群点（Outliers），如果直接按最大值截断，会导致大部分正常数据的精度严重压缩。所以工具会使用一些高级统计学算法来找到最佳截断点Scale：
    • KL 散度（KLD / Entropy）： 寻找一个截断点，使得量化前后的信息熵（数据分布）损失最小（TensorRT 默认视觉模型算法）。
    • Percentile（分位数）： 比如丢弃全网络最大的 0.01%0.01\%0.01% 的数据，只用 99.99%99.99\%99.99% 的最大值作为截断范围。
    • MinMax： 简单粗暴，直接用统计到的绝对最大值。

3. 合并与导出

把计算好的“权重 INT8 矩阵”和“每一层激活值的 Scale 缩放表”打包。

交给 TensorRT 后，推理时数据一进来，就乘以对应的 Scale 变成 INT8 进行硬件加速，出结果时再除以 Scale 变回浮点数。

3 QAT

3.1 具体流程

1. 自动插入“伪量化”节点（Fake-Quantization）

你不需要手动去改写 PyTorch 的网络层。ModelOpt 可以自动扫描你的 PyTorch 模型，在卷积层、全连接层、激活函数等地方自动插入 FakeQuantize 节点。

  • 原理： 在前向传播时，数据会被转换为低精度再转回高精度（模拟 INT8 的精度损失）；在反向传播时，正常的更新梯度。

2. 校准与范围学习（Calibration & Learnable Scales）

量化最难的是确定“截断范围”（Scale）。ModelOpt 提供了多种算法：

  • 它可以在 QAT 开始前，通过少量数据进行校准（Calibration），初始化一个比较好的量化范围。
  • 在 QAT 训练过程中，这个量化范围（Scale）会变成可学习的参数，随着网络权重一起优化，找到最完美的截断点。

3.2 伪量化节点

是:

在 QAT（量化感知训练）期间，普通的 PyTorch 算子（比如卷积层）其实依然在用 FP32（32位浮点数）进行计算。

在前向传播和反向传播中分别扮演不同的角色：

  • 前向传播（Forward）—— 制造伤害（模拟误差）： 当一个完美的 FP32 浮点数（比如 0.342178）流经伪量化节点时，它会执行以下操作：

    1. 量化（Quantize）：根据当前的缩放因子（Scale），把它四舍五入变成 INT8 整数（比如 87）。
    2. 反量化（Dequantize）：立刻把这个 87 再乘回 Scale，变回 FP32 浮点数（比如 0.339843）。

    这个过程故意丢失了尾部的精度（0.342178 变成了 0.339843），这就叫量化噪声。后面的卷积层吃到的就是这个“带有噪声、被污染过”的输入。

  • 反向传播（Backward）—— 绕过惩罚（传递梯度）： 当梯度传回来时，因为四舍五入函数（Round）的导数是 0，伪量化节点会使用一种叫 STE（Straight-Through Estimator，直通估计器） 的技术，直接假装什么都没发生，把后面的梯度原封不动地传过自己，让前面的层能够正常更新权重。

💡 总结它的目的：让模型在训练时，提前体验并适应未来部署到 INT8 硬件上时才会遇到的精度损失，从而在训练中自己调整权重来弥补这个损失。

二、 核心差异深层分析

1. 推理速度（Inference）的断层式碾压（5.5ms vs 1.6ms）

这是本次对比的核心亮点。为什么 TensorRT 能够把推理时间压到不可思议的 1.6ms？

  • 动态范围量化（INT8）：PyTorch 默认使用 FP32（32位浮点数）或 FP16 进行计算。而你的 TRT 引擎使用了 INT8（8位整数）。在显存体积和计算吞吐上，INT8 具有压倒性优势，RTX 3060 的 Tensor Cores 处理 INT8 矩阵乘法的速度远快于浮点数。
  • 计算图融合（Graph Fusion）：PyTorch 在运行时是逐层调用 CUDA 核函数的。TensorRT 在编译阶段（你之前等的 155 秒）将 YOLO 里的 Conv + BatchNorm + ReLU 融合成了一个单一的算子，极大减少了显存与 GPU 寄存器之间的数据拷贝（Memory Bound 优化）。
  • 核心选择（Kernel Selection）：TensorRT 针对你这块 RTX 3060 Laptop 显卡的硬件架构（Ampere 架构），在底层精选了最契合的底层 CUDA 算子。

2. 后处理（Postprocess）为什么变快了？（1.65ms vs 1.25ms）

  • 思考：后处理（如 NMS 非极大值抑制、Mask 原型系数相乘等）通常是在 CPU 或通过普通的 PyTorch 算子在 GPU 上跑的，为什么 TRT 也会变快？
  • 原因：在第二阶段导出 ONNX 过程中，YOLO 的一部分后处理节点（甚至包括部分 Gather/Slice 边界处理）被转换成了高效的 ONNX/TRT 原生算子，或者通过 TensorRT 的编译进行了优化。数据从“模型结束”到“后处理开始”的交接更加紧凑，减少了 CPU/GPU 的同步等待时间。

3. 数据一致性（业务安全）

最让人欣慰的是数据的完全一致。例如：

  • 图片 01：3 apples, 2 carrots, 1 eggplant, 4 pear_greens
  • 图片 02：2 apples, 1 carrot, 1 eggplant, 4 pear_greens

在两套引擎下数量和类别完全恒定。这证明在当前的水果实例分割场景下，TensorRT INT8 量化完全没有引发精度崩塌，你可以非常安全地在生产环境替换掉 .pt 模型。

Fruit 项目 AI 推理性能优化全景备忘录

本策划文档系统性汇总了 Fruit 项目在 AI 模型推理与数据流 上的全量优化项。涵盖已完成的基线构筑、刚刚定位并待实施的运行期重构，以及未来的模型层深度榨干方案。

一、 已完成的基础优化（第一阶段：稳固基线）

核心目标：消除高额的硬件连接与线程冷启动固定开销。

1. 摄像头常驻打开

  • 内容简介：将视频流拉取模块改为常驻守护线程，避免每次 API 请求时重新初始化硬件驱动和建立视频流连接，彻底消除了秒级的硬件唤醒延迟。

2. 模型启动期预热 (Warmup)

  • 内容简介：在系统初始化（main.py）阶段，使用哑数据（Dummy Data）提前触发 GPU 前向传播。规避了首次真实请求时，CUDA 引擎初始化和算子动态加载带来的首帧高延迟。

3. 推理线程常驻

  • 内容简介：构建长寿命的常驻推理线程池，避免在高频 API 请求下频繁创建、销毁 Python 线程所导致的系统上下文切换与 CPU 损耗。

4. 模型推理复用池 (Model Hub)

  • 内容简介：设计跨路径的模型单例复用机制。当不同的检测路径（detection_path）调用相同的底层模型时，共享内存与显存中的同一个模型实例，大幅降低了多路并发时的总显存占用。

二、 刚刚发现并确认的优化（第二阶段：精细重构）

核心目标：消灭运行期（Runtime）热路径上的对象重建、串行阻塞、无谓渲染与轮询抖动。

5. 消除每请求配置更新与 Processor 重建【P0】

  • 内容简介：重构 target_detection.py，绕过会触发文件锁（I/O 竞争）与重算相机内参的 update_detector_config 重型方法。改为在运行期原地（In-place）动态修改 target_classes 属性，让“模型预热”的成果真正留存。

6. 位置检测降帧与多帧 Batch 推理优化【P0】

  • 内容简介：针对水果位置检测（Position）无需滑动窗口计数的特性，将 reading_frames_count 降为 1，消灭串行循环；或在必须多帧时，解耦深度配准逻辑，利用 YOLO 原生 Batch 一次性前向推理，将多帧延迟缩减至接近单帧。

7. 帧获取由 Sleep 轮询改为 Condition 唤醒机制【P2】

  • 内容简介：废除 _get_last_frame 中固定的 time.sleep(0.05) 盲等轮询。在 annotated_hub 写入新帧时引入 threading.Condition 信号通知（notify_all），让推理线程在帧就绪的瞬间被精准唤醒，消除几十毫秒的随机等待延迟。

8. 生产路径按需 plot() 与去除深度图拼接【P1】

  • 内容简介：将耗费大量 CPU 算力的实例分割 plot() 遮罩渲染和左右深度伪彩图拼接做“按需门控”机制。前 N−1N-1N−1 帧纯做矩阵计算，仅在最后一帧或显式开启 Debug 存图时才执行图像可视化绘制。

9. 禁用 InArea 推理的控制台 verbose 打印【P1】

  • 内容简介：将 FruitInAreaFrameProcessor 内部调用模型时的 verbose=True 显式改为 False。消灭高频热路径上往控制台（stdout）打印文本引起的同步 I/O 阻塞。

10. 限制 max_det、固定 imgsz 与本地 half 推理【P2】

  • 内容简介：在 Object Detection 架构 Schema 中沉入新参数：位置场景限制 max_det=1 以断崖式降低 NMS（非极大值抑制）计算耗时；固定 imgsz 规避隐式 letterbox 尺寸缩放；本地 .pt 跑测时开启 half=True（FP16）使 GPU 吞吐翻倍。

三、 未完成的进阶优化（第三阶段：模型与引擎深度挖掘）

核心目标：通过重构编译配置、量化、任务裁剪，将 TensorRT 推理性能榨干到极致。

11. 引擎导出参数调优（零训练成本，最快见效）

  • 内容简介：在 ultralytics 导出 .engine 时进行定制：
    • 矩形输入：将默认 640×640640 \times 640640×640 的方形编译改为匹配相机的矩形 imgsz=(480, 640)，直接减少约 33% 像素的计算量。
    • 静态 Shape：若锁定 Batch 帧数，导出时固定 batch=3（单帧则固定 batch=1），利用静态 Shape 让 TensorRT 针对性挑选最优算子（Tactic Selection），消除动态 Shape 的 Profile 消耗。
    • 启用简化：开启 simplify=True 融合多余的 ONNX 算子。

12. INT8 训练后量化 (PTQ / QAT)

  • 内容简介：在 FP16 基础上推进 INT8 量化，预期可为 Orin/GPU 带来 1.5~2 倍的吞吐飞跃。收集产线几百张真实图片作为标定集（Calibration Dataset）进行 PTQ 导出；若精度（质心坐标）抖动超出预期，则引入量化感知训练（QAT）进行精度补偿。

13. 端到端 NMS 编译进引擎（消除 Host 传输瓶颈）

  • 内容简介：导出时设置 nms=True，利用 TensorRT 的 EfficientNMS_TRT 插件将检测框解码与 NMS 过滤完全融进 GPU 内部。使得模型直接输出过滤后的最终边界框，免除了大张量回传（GPU →\rightarrow→ CPU）与在 Python 层跑 NMS 的严重耗时。

14. 任务模型选型降级（Head 结构裁剪）

  • 内容简介：严格按业务“取什么信息”匹配最轻量的 Model Head。
    • 评估 Line2 主链路，由于其仅提取 BBox 中心点，可将 Segment（分割）模型降级为 Detect（检测）模型，彻底砍掉 Proto Mask 分支与 Mask 上采样计算。

🛠️ 为什么会这样？如何破局？

目前模型呈现这种“蜗牛爬”的涨幅，通常是由以下三个底层原因导致的，你可以对照调整：

1. 负样本的“压迫感”还是不够（当前最可能的原因）

模型学得这么累，说明你当前 Batch 里的负样本或者你手动给的负样本，对模型来说还是太好区分了。

  • 逻辑： 既然负样本很容易被推开，模型只需要稍微调整一点点权重，就能让 Loss 降下去。它没有动力去死磕那些排在第 1 名的“高难度冒牌货”。
  • 药方： 加大 Hard Negatives 的难度。直接去抓你当前这个 400 步模型检索出来的 Top 1 错误文档，作为下一轮训练的硬核负样本。

2. 学习率（Learning Rate）开得太小

Embedding 微调和从头训练不同，如果你的 Learning Rate（LR）设得极低（比如 1e-6 或更小），加上预训练模型本身的权重根基很深，模型在 400 步内基本处于“原地踏步”状态。

  • 药方： 检查你的配置（cfg）。如果是基础的 BERT 级别模型，微调学习率通常在 2e-5 到 5e-5 之间比较健康。如果太小，可以尝试翻倍。

3. Batch Size 的隐形限制

如果你使用的是带有 In-batch Negatives 特性的 Loss（如 MNRL），训练的难度是和 batch_size 强绑定的。

  • 逻辑： Batch Size 越大，当前 Batch 内的负样本就越多，竞争越激烈，模型被迫学得越快。如果你的 batch_size 只有 16 或 32，模型每一步见到的世面太小，指标就会涨得非常缓慢。
  • 药方： 在显存允许的情况下，尽最大可能把 batch_size 轰上去。

6 测试

1. 测试目标

测试的核心目标是验证模型在特定场景下的表征与排序能力：

  • 语义对齐能力： 同一个 Post 对应的多个不同 Query，能否都能在向量空间中精准向该 Post 靠拢？
  • 细粒度区分能力（核心）： 面对“同系列、微小剧情区别/换主角”的相似文本（Hard Negatives），模型能否展现出足够的各向异性（即能够精确区分，不把它们混为一谈）？
  • 线上收益预期： 评估微调模型相比于原始 Baseline 模型，能为实际业务带来多少纯检索质量的提升。

2. 测试方向

测试应当分层进行，主要分为以下两个方向：

  • 方向 A：离线效果评测（Automated Offline Evaluation）
    • 通过静态的测试集（验证集），使用数学指标（如你跑出的 Recall、MRR、NDCG）来评估模型的向量空间质量。
    • 边界专项测试（Stress Test）： 单独抽样出“相似电影换主角”、“极短 Query”、“多音字实体”等高频失败场景进行定向评测。
  • 方向 B：线上模拟/系统级评测（System-level Evaluation）
    • 混合检索实验： 将 Embedding 与 BM25 进行传统倒排融合（如 RRF 融合算法），测试在引入微调 Embed 后，整体混合检索的 Top K 覆盖率。
    • 推断耗时测试（Latency Test）： 统计模型在 GPU/CPU 上的 Embedding 向量化耗时（通常要求单条 <10ms<10\text{ms}<10ms），确保微调引入的结构没有让模型变慢。

  • 提头能力指标：Accuracy@1Accuracy@1Accuracy@1 / Recall@1Recall@1Recall@1 / MRR@10MRR@10MRR@10
    • 这是你目前的痛点。如果模型能把正确的正样本精准排在第一名，MRR 会显著拔高。
  • 召回圈能力指标：Recall@5Recall@5Recall@5 / Recall@10Recall@10Recall@10
    • 验证模型是否能把正确的候选集大范围捞出。目前你的模型在此指标上已经表现优异（R@10>80%R@10 > 80\%R@10>80%）。
  • 全局排序质量：NDCG@10NDCG@10NDCG@10 / MAP@10MAP@10MAP@10
    • 利用折扣增益，综合评估前 10 个坑位中，正样本排名的合理性。
  • 统计学监控：Cosine Similarity 分布
    • 计算正样本对的平均相似度（应尽量接近 1）与 Hard Negatives 的平均相似度（应被推远，拉开 Margin 分布）。

测试集的构建必须严格与训练集隔离（No Data Leakage），但结构要对标真实业务：

线程（Thread）

线程是操作系统提供的最小执行调度单位之一，属于进程内部的执行流。

一个进程可以包含多个线程，这些线程共享进程的内存空间，由操作系统进行调度执行。

1. 线程的本质

线程可以理解为：

进程内部的一条执行路径

特点：

  • 由操作系统调度（OS scheduler）
  • 属于内核级并发（kernel-level concurrency）
  • 多线程可以在多核 CPU 上实现并行执行

2. 线程与进程的关系

  • 进程：资源分配单位（内存、文件句柄等）
  • 线程：执行单位（代码执行流）

一个进程中可以包含多个线程：

特点：

  • 线程共享进程内存
  • 线程之间通信简单（但也更容易出错）

3. Python 中的线程

Python 使用 threading 模块支持多线程：

说明：

  • start()：启动线程
  • join()：等待线程结束

4. 线程调度机制

线程由操作系统进行调度：

  • 抢占式调度（preemptive）
  • CPU 时间片轮转
  • 多线程可以“看起来同时运行”

5. Python 线程的限制（GIL）

Python 有一个重要限制：

GIL（Global Interpreter Lock，全局解释器锁）

影响：

  • 同一时刻只能有一个线程执行 Python 字节码
  • 多线程无法真正并行执行 CPU 计算

6. GIL 的影响

✔️ 适合场景（IO 密集）

  • 网络请求
  • 文件读写
  • 数据库操作

原因：

线程在 IO 阻塞时会释放 GIL

❌ 不适合场景（CPU 密集）

  • 图像处理
  • 深度学习计算
  • 大规模数值计算

原因：

线程无法真正并行执行 CPU 计算

7. 线程的优缺点

优点

  • 创建开销比进程小
  • 适合 IO 并发
  • 共享内存，通信方便

缺点

  • GIL 限制并行能力
  • 线程安全问题（竞争条件）
  • 调试复杂

8. 线程 vs 协程 vs 进程（核心对比）

模型 调度方式 并行能力 开销 适用场景
进程 OS调度 强（多核） 高 CPU密集
线程 OS调度 受GIL限制 中 IO并发
协程 用户态调度 无并行 极低 高并发IO

Python 线程库提供基于操作系统调度的并发能力，适合 IO 密集型任务，但受 GIL 限制无法实现 CPU 级真正并行，实际开发中更推荐使用线程池进行管理。
