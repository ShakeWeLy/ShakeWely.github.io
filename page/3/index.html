第四章 智能体经典

4.1 React

ReAct 像一个经验丰富的侦探，根据现场的蛛丝马迹（Observation）一步步推理，随时调整自己的调查方向；

ReAct范式通过一种特殊的提示工程来引导模型，使其每一步的输出都遵循一个固定的轨迹：

  • Thought (思考)****： 这是智能体的“内心独白”。它会分析当前情况、分解任务、制定下一步计划，或者反思上一
  • 步的结果。
  • Action (行动)****： 这是智能体决定采取的具体动作，通常是调用一个外部工具，例如 Search['华为最新款手
  • 机’] 。
  • Observation (观察)****： 这是执行 Action 后从外部工具返回的结果，例如搜索结果的摘要或API的返回值。

智能体将不断重复这个 Thought -> Action -> Observation 的循环，将新的观察结果追加到历史记录中，形成一个

不断增长的上下文，直到它在 Thought 中认为已经找到了最终答案，然后输出结果。这个过程形成了一个强大的协同

效应：推理使得行动更具目的性，而行动则为推理提供了事实依据。

  • 需要外部知识的任务：如查询实时信息（天气、新闻、股价）、搜索专业领域的知识等。
  • 需要精确计算的任务：将数学问题交给计算器工具，避免LLM的计算错误。
  • 需要与API交互的任务：如操作数据库、调用某个服务的API来完成特定功能。
  1. 整个机制的稳定运行建立在一个精心设计的提示词模板之上。模板中的任何微小变动，甚至是用词的差异，都可能影响 LLM 的行为。

4.2 Plan-and-Solve

Plan-and-Solve 则更像一位建筑师，在动工之前必须先绘制出完整的蓝图（Plan），然后严格按照蓝图来施工（Solve）

Plan-and-Solve 将整个流程解耦为两个核心阶段：

  1. 规划阶段 (Planning Phase)： 首先，智能体会接收用户的完整问题。它的第一个任务不是直接去解决问题或调用工具，而是将问题分解，并制定出一个清晰、分步骤的行动计划。这个计划本身就是一次大语言模型的调用产物。

  2. 执行阶段 (Solving Phase)： 在获得完整的计划后，智能体进入执行阶段。它会严格按照计划中的步骤，逐一执行。每一步的执行都可能是一次独立的 LLM 调用，或者是对上一步结果的加工处理，直到计划中的所有步骤都完成，最终得出答案。

尤其适用于那些结构性强、可以被清晰分解的复杂任务，例如：

  • 多步数学应用题：需要先列出计算步骤，再逐一求解。
  • 需要整合多个信息源的报告撰写：需要先规划好报告结构（引言、数据来源A、数据来源B、总结），再逐一填充内容。
  • 代码生成任务：需要先构思好函数、类和模块的结构，再逐一实现。

4.3 Reflection

Reflection 机制的核心思想，正是为智能体引入一种事后（post-hoc）的自我校正循环

其核心工作流程可以概括为一个简洁的三步循环：执行 -> 反思 -> 优化。

  1. 执行 (Execution)：首先，智能体使用我们熟悉的方法（如 ReAct 或 Plan-and-Solve）尝试完成任务，生成一个初步的解决方案或行动轨迹。这可以看作是“初稿”。
  2. 反思 (Reflection)：接着，智能体进入反思阶段。它会调用一个独立的、或者带有特殊提示词的大语言模型实例，来扮演一个“评审员”的角色。这个“评审员”会审视第一步生成的“初稿”，并从多个维度进行评估，例如：
    • 事实性错误：是否存在与常识或已知事实相悖的内容？
    • 逻辑漏洞：推理过程是否存在不连贯或矛盾之处？
    • 效率问题：是否有更直接、更简洁的路径来完成任务？
    • 遗漏信息：是否忽略了问题的某些关键约束或方面？ 根据评估，它会生成一段结构化的反馈 (Feedback)，指出具体的问题所在和改进建议。
  3. 优化 (Refinement)：最后，智能体将“初稿”和“反馈”作为新的上下文，再次调用大语言模型，要求它根据反馈内容对初稿进行修正，生成一个更完善的“修订稿”。
  • 生成关键的业务代码或技术报告。
  • 在科学研究中进行复杂的逻辑推演。
  • 需要深度分析和规划的决策支持系统。

Reflection 的价值在于：

  • 它为智能体提供了一个内部纠错回路，使其不再完全依赖于外部工具的反馈（ReAct 的 Observation），从而能够修正更高层次的逻辑和策略错误。
  • 它将一次性的任务执行，转变为一个持续优化的过程，显著提升了复杂任务的最终成功率和答案质量。
  • 它为智能体构建了一个临时的**“短期记忆”。整个“执行-反思-优化”的轨迹形成了一个宝贵的经验记录，智能体不仅知道最终答案，还记得自己是如何从有缺陷的初稿迭代到最终版本的。更进一步，这个记忆系统还可以是多模态的**，允许智能体反思和修正文本以外的输出（如代码、图像等），为构建更强大的多模态智能体奠定了基础。

流程

当用户提出问题时，完整的工具选择流程如下：

  1. 工具发现阶段：MCP Client 连接到 Server 后，首先调用list_tools()获取所有可用工具的描述信息（包括工具名称、功能说明、参数定义）

  2. 上下文构建：Client 将工具列表转换为 LLM 能理解的格式，添加到系统提示词中。例如：

  3. 模型推理：LLM 分析用户问题和可用工具，决定是否需要调用工具以及调用哪个工具。这个决策基于工具的描述和当前对话上下文

  4. 工具执行：如果 LLM 决定使用工具，Client 通过 MCP Server 执行所选工具，获取结果

  5. 结果整合：工具执行结果被送回给 LLM，LLM 结合结果生成最终回答

这个过程是完全自动化的，LLM 会根据工具描述的质量来决定是否使用以及如何使用工具。因此，编写清晰、准确的工具描述至关重要。

进程池

pool

进程复用：进程池中的工作进程一旦创建，会持续存活直到进程池关闭，可反复处理多个任务，无需每次执行任务都创建新进程。

任务排队与调度：当提交的任务数量超过进程池的工作进程数时，未被执行的任务会进入任务队列排队，等待空闲工作进程来处理。

pool.异步apply

同步 apply()：提交任务后，会阻塞主进程，直到该任务执行完成并返回结果，才能继续执行后续代码（效率较低，适合简单单任务场景）。

异步 apply_async()：提交任务后，不会阻塞主进程，主进程可以继续执行后续代码，任务在子进程中后台运行，结果可通过回调函数或返回值对象获取（效率较高，适合多任务并行场景）。

pool.close

pool.close() 只是 “禁止提交新任务”，不会终止现有任务，也不会释放进程池资源。

通常 pool.close() 会与 pool.join() 配合使用（join() 用于阻塞主进程，等待进程池中所有任务执行完成并释放资源）。

.daemon 对应的是守护进程（Daemon Process）

生命周期依赖主进程：守护进程会随着主进程的退出而自动终止，无论它自身的任务是否执行完成。这是守护进程最核心的特征，也是它与普通子进程的核心区别。

无法创建子进程：守护进程本身不能再创建新的子进程（如果尝试创建，会抛出相关异常或导致不可预期的行为）。

无终端关联：守护进程通常脱离终端运行，不与用户交互，这也是它与普通后台运行进程的共性之一，但并非其核心定义。

Agent记忆管理

  • 短期记忆：类似于我们临时记住一个电话号码，过一会儿就可能忘记。大模型通过在输入中嵌入提示语句（prompt），借助自身强大的上下文理解能力来“记住”最近的对话内容。但这种记忆会随着上下文窗口的限制而被覆盖或遗忘。
  • 长期记忆：更像是我们记住一段旅行经历，或者对某个朋友的长期印象。智能体通过建立外部记忆库来实现知识和经验的持久化存储，可以在需要时随时检索出来，帮助它更高效地解决问题

0 本质

先向量化–> 存储 --search -->rerank

1. 核心机制（你已点明的部分）

  • 序列化：将对话历史、知识、用户画像等压缩进有限上下文（Prompt）。
  • 检索：从向量库、数据库或记忆中查找相关信息。
  • TopK：选择最相关的几条信息。
  • 拼接：将检索结果与原问题拼接，送入模型。

2. 超越“简单拼接”的关键演进

虽然基础操作类似，但先进系统在以下方面做了大量工作：

a. 记忆的层次与结构

  • 短期记忆：当前会话的上下文（直接拼接）。
  • 长期记忆：
    • 向量记忆：语义搜索，处理非结构化知识。
    • 图记忆：存储实体、关系，用于推理（如知识图谱）。
    • 结构化记忆：SQL/键值存储，存储精确信息（如用户偏好）。

Memory Bank

MemoryBank 包含三个核心模块：

  1. 记忆存储：保存对话记录、事件总结和用户个性分析，就像建立一个多层次的记忆档案。
  2. 记忆检索：根据上下文快速找到相关的“回忆”。它使用一种稠密向量检索方法（类似 Dense Passage Retrieval, DPR），把每条记忆片段编码成向量，再用 FAISS 进行高效搜索。

2025年12月22日 ConvNeXt

ResNeXt

Inception那边把ResNet拿来搞了Inception-ResNet，这头ResNet也把Inception拿来搞了一个ResNeXt，主要就是单路卷积变成多个支路的多路卷积，不过分组很多，结构一致，进行分组卷积。

https://zhuanlan.zhihu.com/p/32913695

Inception

左边是ResNet的基本结构，右边是ResNeXt的基本结构：

ConvNeXt

从传统 ResNet 逐渐演变到具有Transformer特点的卷积神经网络的演变路径，仍然基于卷积神经网络架构，但它在设计上融入了一些Transformer的元素或特性，使得它在某种程度上与Transformer相似，但仍然保持了ConvNet的基本性质。

https://zhuanlan.zhihu.com/p/1928810982915941594

1 超参数调优：重塑 ResNet

ConvNeXt 的核心思想其实就是：对 ResNet 架构进行系统性的超参数调优。具体来说，作者主要从五个方面进行了实验探索：

  1. 宏观结构设计（Macro Design）
  2. 引入 ResNeXt 模块（ResNeXt）
  3. 反向瓶颈结构（Inverted Bottleneck）
  4. 使用大卷积核（Large Kernel）
  5. 微观结构设计（Micro Design）

宏观设计（Macro Design）

将 ResNet 的阶段比例（stage ratio）调整为与 Swin-T 架构一致，也就是 1:1:3:1。

ResNeXt 化（ResNeXt-ification）

主要是在 ResNet 的 bottleneck 模块中引入了组卷积（group convolution）

倒置瓶颈结构（Inverted Bottleneck）

ResNet属于 “宽 → 窄 → 宽” 的布局，因此被称为“瓶颈结构”。但 ConvNeXt 并没有采用这个经典设计，而是引入了“倒置瓶颈”（Inverted Bottleneck），也就是 “窄 → 宽 → 窄”，这个结构灵感来自 Transformer 架构中的前馈网络层。

卷积核大小

让深度卷积（depthwise convolution）放到了模块的开头，这一设计灵感来源于 Transformer 结构，在 Transformer 中多头自注意力层（MSA）会放在前面，后面才是前馈网络层（MLP）。

微观设计

论文中调优的最后一个方面是“微观设计”，主要是网络细节层面的调整。和之前一样，这些参数大多借鉴了 Transformer 的设计。首先，作者用 GELU 激活函数替代了 ReLU。虽然替换后准确率保持不变（仍是 80.6%），但他们决定在后续实验中采用 GELU。

之后，他们发现减少激活函数的使用次数能提升准确率。具体做法是，不再在 ConvNeXt 块中的每个卷积层后都使用 GELU，而只在两个点卷积层之间使用一次。这样一改，准确率提升到了 81.3%，已经追平了 Swin-T 架构，而且计算复杂度更低（4.2 vs 4.5 GFLOPS）。

接下来是批量归一化（Batch Normalization，BN）层的调整。传统 CNN 架构常用 Conv-BN-ReLU 结构，ResNet 也沿用了这个设计。但作者们选择只用一层 BN，放在第一个点卷积层之前。这个改动使准确率微升至 81.4%，略微超过了 Swin-T。

尽管如此，参数调优还没结束，接着用层归一化（Layer Normalization）替代了 BN，准确率再次提升了 0.1%，达到 81.5%。

所有这些微观设计的改动最终汇总成了图 5（最右侧）的架构示意图。从图中可以清楚看出 ConvNeXt 块与 Swin Transformer 及 ResNet 块的不同之处。

V3

DINOv2 让我们看到了自监督学习（SSL）超越弱监督学习的希望，那么 DINOv3 则是一种降维打击。它不仅把模型参数量推到了 7B 的大语言模型级别

1. 自监督与弱监督

自监督：
👉 监督信号从数据本身自动构造，不需要人工标签

弱监督：
👉 有标签，但标签不精确 / 不完整 / 有噪声

常见弱监督形式

1️⃣ 标签不精确（最常见）
  • 只有图像级标签，没有 bbox / mask
  • 如：这张图“有猫”，但不知道猫在哪

📌 弱监督目标检测、弱监督分割

2️⃣ 标签不完整
  • 只标一部分样本
  • 如：数据集中只有 10% 有标注
3️⃣ 标签有噪声
  • 自动生成标签
  • 爬虫数据、规则生成标签

📌 工业场景、日志规则系统（你现在做的 SQL 规则也很像）

典型方法

方法 说明
MIL Multiple Instance Learning
CAM Class Activation Map
伪标签 模型预测 → 当新标签
规则 + 学习 人工规则生成弱标签

1.1 自监督 ≠ 传统无监督

自监督 = 用无标签数据 + 人为设计的监督目标
无监督 = 没有监督目标，主要做结构发现

👉 自监督是“披着无监督外衣的监督学习”

关键差别在「有没有监督信号」

方式 有无标签 有无明确目标
无监督 ❌ ❌
自监督 ❌ ✅（伪标签）
有监督 ✅ ✅

举个直观例子（视觉）

  • 无监督：
    • K-means 聚类
    • PCA / ICA
    • 只是“发现结构”
  • 自监督：
    • 预测旋转角度
    • 图像遮挡 → 复原
    • 对比学习（谁和谁是同一张）

在过去，我们认为：通用模型（Generalist）不如专用模型（Specialist）。 你想做语义分割？用 Mask2Former 微调。想做深度估计？用 Depth Anything。想做视频跟踪？设计专门的时序模块。

但 DINOv3 告诉你：不需要。直接冻结了 DINOv3 的骨干网络，仅在后面接一个简单的线性解码器（Linear Decoder）

二、 核心痛点：Scaling 的“特征坍塌”悖论

把 ViT 模型做大（比如从 Base 到 Giant），并用更多数据训练更久时：

  1. 全局指标变好：ImageNet 分类准确率上升（模型更懂语义了，知道这是“狗”）。
  2. 局部指标变差：像素级的稠密特征（Dense Features）开始退化，特征图变得杂乱无章，丢失了物体边界信息

这就是**“语义增强与几何丢失”的博弈**。模型为了追求极致的分类能力，倾向于把特征抽象化，从而牺牲了空间上的结构一致性。

DINOv2 通过引入 Register Tokens 缓解了高频噪声，但在 7B 这个参数量级下，特征依然会崩塌。

三、 技术解密：Gram Anchoring（格拉姆锚定）

DINOv3 的核心贡献，就是用一种极其优雅（甚至有点简单）的方法解决了上述悖论。这个方法叫 Gram Anchoring。

1. 思想实验：保持队形

想象一群士兵（Patch tokens）在训练。

  • 普通的 SSL：教官说“跑到那个高地上（学习高级语义）”。结果士兵们跑是跑到了，但队形散了，乱成一团。
  • Gram Anchoring：教官说“你们去高地，但必须保持现在的相对队形不变”。

2. 数学原理

作者引入了一个**“Gram Teacher”**。这通常是一个训练早期（Early Stage）的模型副本，或者是经过高分辨率处理后的模型。

关键点在于： 它不强求学生模型的特征 与老师一模一样（那样就学不到新东西了），而是强求特征之间的关系结构（Gram Matrix） 与老师保持一致。

这使得 DINOv3 可以在任意高维的语义空间里遨游，同时被“锚定”住坚实的几何结构。结果就是，DINOv3 的特征图（PCA可视化）干净得像是有监督分割模型的 Ground Truth。

四、工程能力

  1. 恐怖的数据清洗： 构建了一个 LVD-1689M 数据集（16.89亿张图）。但这不仅仅是爬虫，他们使用了极其复杂的聚类（Clustering）和检索（Retrieval）管道，确保数据的多样性和质量。这再次证明：Data is the new code.
  2. 7B 参数的 ViT： 这不是简单的堆叠层数。他们使用了 RoPE（旋转位置编码），并改进了注意力机制中的偏置策略，使得模型可以天然适应多尺度分辨率（从 224 到 4096 甚至更高）。
  3. 蒸馏（Distillation）的艺术： “天塌了”的另一个原因是算力焦虑。但好消息是，Meta 将 7B 巨无霸的能力蒸馏到了一系列小模型（ViT-S, ViT-B, ViT-L）上。 重点来了： 蒸馏后的 DINOv3-ViT-L，性能已经吊打了之前的 DINOv2-ViT-Giant。这意味着我们普通开发者也能用上 SOTA 级别的特征。

方式 A：copy环境: Electron 启动独立 Python 进程

1. venv 的原理

venv 并不是完全自包含的 Python，它依赖创建时 系统 Python 的文件来构建：

  • Scripts/python.exe → 指向 venv 内的可执行文件（拷贝或软链接）
  • Lib/ → 包含标准库
  • pyvenv.cfg → 记录 home（原系统 Python 位置）和 executable

关键是：

当你在其他机器运行 venv：

  • 只要 venv 内的 python.exe 和 Lib 完整，路径不同一般不会报错。
  • 如果 venv 内缺少标准库或 DLL，就会报错 ModuleNotFoundError: encodings 或启动失败。

vеnv 依赖系统 Python 的路径（pyvenv.cfg 指向打包路径）

  • home 指向你本地的系统 打包的Python路径
  • 客户机上路径不同 → venv 找不到标准库 → 报错 ModuleNotFoundError: encodings
  • ⚠️ 这是之前遇到的错误的根本原因 → 安装新环境并修改对应的path文件

2. embeddable python特性:

2.1 库编译问题

  1. 依赖
    • opencv-python 本身提供了预编译 wheel，但有些依赖（如 matplotlib）可能需要 源代码编译，尤其在缺少 wheel 或版本不匹配的情况下
    • matplotlib 依赖 cycler、kiwisolver、pillow 等，某些组件可能需要 C/C++ 编译工具
    • mesonpy 是最近 matplotlib 构建系统的一部分，用于编译扩展
  2. 嵌入式 Python 不包含编译环境
    • 没有 Visual Studio C++ Build Tools
    • 没有 python-config、make、ninja 等工具

所以在 嵌入式 Python 下 pip install opencv-python 或 matplotlib 就会失败，因为它需要编译环境，嵌入式 Python 只能提供一个纯净的解释器和标准库。

2.2可行解决方案

  1. 使用预编译 wheel（

    • 下载适合你 Python 版本和架构的 .whl 文件，直接安装：

    • 这样就不用本地编译了。

    • 你可以在 PyPI opencv-python 找到对应 wheel。

  2. 下载相关编译工具集
