介绍

What

模型上下文协议: 定义了应用程序和 AI 模型之间交换上下文信息的方式。

这使得开发者能够以一致的方式将各种数据源、工具和功能连接到 AI 模型（一个中间协议层），就像 USB-C 让不同设备能够通过相同的接口连接一样。

Why

function call 平台依赖性强，不同 LLM 平台的 function call API 实现差异较大。例如，OpenAI 的函数调用方式与 Google 的不兼容，开发者在切换模型时需要重写代码，增加了适配成本。

官方也提供了非常多现成的 MCP Servers，你只需要选择你希望接入的工具，然后接入即可。

  • Awesome MCP Servers
  • MCP Servers Website
  • Official MCP Servers

How

其实就是把tool变成工具集…

MCP 的核心就三样东西：

Server：对外暴露工具的服务端，本质上是一个 Python 脚本，声明"这些函数可以被 LLM 调用"，跑起来之后就在监听请求。

Tool：希望 LLM 使用的函数，可以是任何东西：查天气、查数据库)、发邮件。这跟写普通 Python 函数没什么区别，加个装饰器剩下的交给 MCP。

Client：连接 Server 并调用工具的客户端。生产环境里一般就是 LLM 应用本身。测试阶段可以用 FastMCP 自带的客户端，开箱即用。

2026年3月3日 agent上下文工程

1

Context Engineering

https://news.qq.com/rain/a/20260226A076NP00

模型出错往往不是因为理解不了指令，而是因为看到了太多不相关的信息、相互矛盾的数据，或者缺失了关键事实。

Context engineering 把上下文当作一条动态管道来处理，而非一段静态提示词：

  1. 选对文档而不是全量灌入；
  2. 将长文档压缩为面向任务的摘要；
  3. 在检索之前重新表述模糊的用户查询；
  4. 跨会话注入记忆和用户状态；
  5. 用实时工具和数据锚定答案；组织所有输入，让模型知道什么最重要。

0 层次化布局：结构本身就在传达重要性

1 选对文档而不是全量灌入；

  1. 相关性重排：初始搜索基于向量相似度或关键词匹配返回前50个结果，但相似不等于相关。交叉编码器会把查询和每个文档放在一起联合阅读，重新排序。速度慢一些准确度高得多，重排之后只保留前5个。
  2. 冗余消除：同一个概念在文档库里出现在多个地方是常态，比如营销材料、技术规格、FAQ都可能提到同一功能。用 Embedding 对相似文本块做聚类，余弦相似度超过0.9的基本就是重复内容删掉一个即可。模型不需要看同一个事实10遍。
  3. 任务感知过滤：利用元数据做筛选。每个文档都应打上标签：文档类型、最后更新日期、产品版本、地区、部门。查询进来时按相关维度过滤。

2 将长文档压缩为面向任务的摘要；

把长文档放进上下文之前，将其压缩成面向当前任务的密集摘要：不是通用摘要，而是针对当前查询定制的摘要。

三种压缩策略各有侧重。

  • 带约束的LLM摘要：不要只说"总结这个文档"，而是说"总结这个文档，只保留2025年1月之后关于定价变更的事实"。约束条件指明了保留什么、丢弃什么。每个检索到的文档根据查询生成各自的约束。产出从3000个 Token 缩减到5–10个要点。
  • 句子级评分：用较小的模型（如BERT变体）为每个句子计算与查询的相关性分数，按分数排序后只保留前20%。这种方法叫Context-Preserving Compression，速度快，效果好，自动留下最相关的信息。
  • 层次化摘要：适合非常长的文档。先按章节分块每个章节独立生成摘要，再把这些摘要归纳成一个元摘要。最终形成三级结构，完整文档 → 章节摘要 → 最终摘要。根据上下文预算选用合适的层级。

3 在检索之前重新表述模糊的用户查询

三种可行的模式。

澄清优先（适用于智能体场景），与其猜用户什么意思不如直接问。智能体回复："要比较业绩表现，需要明确几个信息——哪个时间段？包含哪些竞争对手？最关注哪些指标（收入、利润还是市场份额）？"用户给出具体条件后，检索随之变得精确。这种策略只适用于多轮对话的智能体，单次问答系统用不上。但在智能体场景下效果很好——用户并不介意回答两三个澄清问题，如果换来的是更准确的答案。

HyDE（Hypothetical Document Embeddings）用户问"产品最新的改进有哪些"，不直接用这个问题去搜索，而是让LLM先生成一段假答案：“最新的产品改进包括重新设计的仪表板、40%的加载速度提升、新增的协作功能和增强的移动端应用。“把这段假答案做 Embedding 后用于检索。为什么有效？因为假答案的措辞和实际文档的措辞一致。文档里不会写"最新的改进是什么”，而会写"重新设计了仪表板”“加载时间缩短了40%”。假答案的 Embedding 比原始问题的 Embedding 更贴近真实文档。

多查询扩展，对原始查询生成3–5个改写版本。“最新产品改进"可以展开为"最近的产品更新”“本季度发布的新功能”“产品增强变更日志”“2.0版本有什么新内容”。每个查询分别检索，合并去重。这种方式能覆盖语义变体和不同的表述习惯。

举个实际例子。用户问"上季度的表现与竞争对手相比如何"。

这个问题里缺了太多信息：哪些竞争对手？哪一年的上季度？衡量什么指标——收入、利润、市场份额还是用户增长？

LLM将其**重写为"比较2024年第四季度（2024年10月至12月）公司X与竞争对手A、B、C在内部财务报告中的收入增长和利润率"。**注意具体程度——精确的时间段、精确的竞争对手、精确的指标、明确的数据来源。检索时还会结合记忆中已知的竞争对手名单（层次化布局的用户档案部分记录了该用户之前多次查询过竞争对手A和B）。

最终上下文对齐的是用户的意图，而非用户键入的字面内容。LLM拿到的是精确数据，不是模糊相关的内容。

4 记忆与状态：保留的是关系，不只是事实

每轮对话结束后做一次LLM摘要——“用户问了什么？提供了什么？用户表达了哪些偏好或需求？”——将摘要与 Embedding 一起存入向量数据库。每轮对话开始前，用当前查询在历史情景摘要库中做向量搜索，取回最相关的3条，再从另一张表加载稳定偏好（这些不需要向量搜索，每次都带上），全部插入层次化布局的 [User Profile / Memory] 区块。

三种记忆类型各有分工。

  1. 情景记忆，即过去对话的摘要。例如："上次会话讨论了为法律文档构建RAG系统，用户关心的是如何处理100多页的合同，最终决定采用512 Token 块配合50 Token 重叠的语义分块策略。"注意，这不是完整的对话记录，而是一份200 Token 左右的摘要，只保留了关键内容。
  2. 语义记忆，存储在向量数据库中的过去交互记录。例如："用户3周前问过关于HDFC的类似问题，当时问的是季度收益，当前查询是关于股息公告，两者都涉及HDFC的财务表现，可以复用之前查询中关于公司基本面的上下文。"语义记忆的价值在于发现模式：用户依次问了HDFC的收益、竞争对手、风险因素，可以判断他正在对HDFC做深度研究，从而主动推送相关信息。
  3. 偏好记忆，很少变化的稳定事实。“用户是初学投资者”“偏好TypeScript”“风险承受能力低”“在医疗保健领域工作”“位于孟买时区”。这些事实影响每一次交互——初学者得到更简洁的解释，低风险用户和高风险用户收到的建议完全不同。

2.1 优化 LLM 的二维思维模型

当 agenticsystem 或单次 LLM 调用的输出不及预期时，问题的根源往往可以归结为两个方面:

2.2 两个简单的示例

示例一: 缺失上下文的代价

第二种的上下文:

信息性上下文(Informational):

[Contact Data]: 识别发件人 Jim 是重要合作伙伴。

行动性上下文(Actionable):

send_calendar_invite 工具的描述

基于这个完整的上下文，它能生成一个真正高效的回应

“Hi Jim! 我明天日程完全满了。周四上午有空，你看方便吗?我发了一个暂定邀请，如果时间合适请确认。

示例二: 上下文退化的挑战

一种朴素的策略: 为了保证模型“无所不知"，系统将每一次交互都记录下来——每一条用户指令、文件读取、编译错误、成功的工具调用–并将这整段历史作为上下文，在每次调用 Agent 时都完整地传递给LLM.

必然出现的失败级联

1.性能下降: 首先，性能会悄然下降。早期任务中1无关紧要的细节(例如一次已解决的语法错误)会不断稀释当前步骤所需的核心信息，造成上下文干扰(Context Distraction)

2.成本与延迟激增: 随着上下文线性增长，每次API调用的 Token 数量急剧膨胀，导致成本失控和更高的延迟。

3.最终崩溃: 最终，系统将撞上架构限制–上下文溢出(Context Overflow)。当累积的信息总量超过模型的上下文窗口上限(无论是 200K还是1M tokens)，API调用将直接失败，可能导致任务中断，或因信息截断而引向错误的结果。

3.How? The Best Practice of Context Engineering

3.2 上下文工程的最佳实践

写入(Write)

写入主要是将上下文持续久化，超越上下文窗口的限制在未来按需取用。通常情况下分为:

  1. 会话内写入(Session-levelWrite): Agent 将中间思考、计划或临时数据写入一个会话内的草稿纸(Scratchpads)。这是一种轻量级的、非持久化的写入，用于管理当前任务的复杂性。
  2. 持久化写入(Persistent Write): 系统将具有长期价值的信息(如用户偏好总结、关键事实)写入外部的记忆(Memory)系统，如向量数据库或知识图谱。

这实现了跨会话的知识积累。例如，ChatGPT和Cursor等应用通过这种方式，让 Agent在与用户的持续交互中“学习"和“成长"，用户在解决某些问题时无需手动引入上下文。

Anthropic也曾在博客中建议，Subagent output to a filesystem to minimize the 'game of telephone. 通过把 subagent 的输出写到文件以避免无意义的上下文传递，上下文窗口占用等。

选取(Select)

选取的目的，是在每次 LLM 调用前，从所有可用的信息源中，动态地拉取与当前子任务最相关的信息。这是保证上下文信噪比的关键。

上下文工程中的选取包括三类:

  1. 确定性选取(Deterministic Select): 指根据预设规则加载上下文。例如，编码 Agent 在启动时，固定加载项目根目录下的CLAUDE.md文件，这是一种简单高效的先验知识注入。
  2. 模型驱动选取(Model-driven Select): 当可用信息源过多时(如海量工具或文档)，可以利用模型自身的能力进行筛选。
  3. 检索式选取(Retrieval-based Select): 这是最主流的方式，其核心范式是通过相似度检索，从记忆、草稿纸或外部知识库中选取信息。因此，选取操作的成败，在很大程度上依赖于底层检索系统的质量。

压缩（Compress)

压缩的目的，是在信息进入上下文窗口之前，对其进行有损或无损的压缩，用更少的 Token 承载最核心的信号。这是在上下文窗口容量有限的情况下，容纳更多有效信息的直接手段。

当上下文窗口即将达到容量上限时，这些系统通常会启动"auto-compact"机制

  1. 历史内容压缩（如图左侧所示）
  2. 工具调用链压缩
  3. 采用经过专门调优的"上下文压缩大语言模型"来实现信息压缩，
  4. 另有修剪策略: 如硬截断超限历史，代价是失去部分语境。

单例模式

原因主要有以下几点：

1. 节省系统资源

有些类的实例化过程会消耗大量资源（比如数据库连接池、线程池、配置文件管理器、日志管理器）：

  • 例如：一个数据库连接池的创建需要初始化连接数、配置超时时间、建立底层网络连接，若每次操作数据库都新建一个连接池实例，会导致内存溢出、数据库连接数耗尽。
  • 单例模式通过复用唯一实例，避免了重复创建 / 销毁实例的资源开销，提升程序运行效率。

2. 保证数据一致性

当多个地方操作同一个 “全局状态” 的对象时，多个实例可能导致数据冲突或不一致：

  • 例如：一个应用的配置管理器，若存在多个实例，当其中一个实例修改了配置项（如切换环境），其他实例可能仍使用旧配置，导致程序行为异常；

3. 提供全局统一的访问入口

单例模式既避免了全局变量的安全性问题（全局变量易被随意修改），又能像全局变量一样让程序任意位置便捷访问该实例：

  • 例如：日志工具类，整个应用的日志输出都通过同一个单例实例完成，能保证日志的输出顺序、格式统一，且无需在每个类中都初始化日志对象。

4. 控制实例的创建时机（懒加载）

单例模式支持 “懒汉式” 实现（用到时才创建实例），而非程序启动时就初始化所有重量级对象，进一步优化程序启动速度和内存占用。

什么情况下不适用

1. 需要多实例的场景（最核心的不适用场景）

如果业务逻辑本身就要求一个类能创建多个独立的实例，使用单例会直接破坏业务逻辑：

  • 示例 1：数据库连接（注意不是 “连接池”）—— 一个应用可能需要同时连接多个不同的数据库（如 MySQL、Redis、Oracle），每个连接都是独立的，若用单例只能创建一个连接，无法满足多数据库操作；
  • 示例 2：用户会话（Session）—— 每个登录用户都需要一个独立的会话对象存储个人信息，若用单例，所有用户会共享同一个会话，导致数据混乱；
  • 示例 3：文件操作对象 —— 同时读写多个文件时，每个文件需要一个独立的文件流实例，单例会导致文件操作互相干扰。

2. 高并发 / 分布式场景（单例的 “唯一性” 失效或引发问题）

  • 分布式系统：单例的 “唯一” 仅局限于单个 JVM 进程，在集群 / 分布式环境中，每个节点都会创建一个单例实例，此时 “全局唯一” 的特性完全失效；
  • 高并发写操作：单例的唯一实例若被多线程频繁修改状态，需要加锁保证线程安全，而锁会导致并发性能下降（甚至出现死锁），此时不如创建多实例避免锁竞争。

3. 不利于测试 / 扩展的场景

单例模式的 “全局唯一” 和 “静态绑定” 特性，会让代码耦合度升高，大幅增加测试和扩展的难度：

  • 单元测试：单例的状态会在测试用例之间共享（比如前一个测试修改了实例的属性，后一个测试会读到脏数据），无法实现 “隔离测试”；
  • 代码扩展：单例模式本质上是 “硬编码” 的唯一实例，若后续业务需要改为多实例，需大幅修改代码（违背 “开闭原则”）；
  • 依赖注入（DI）：现代框架（如 Spring）提倡依赖注入解耦，而单例的全局访问（getInstance()）会让代码紧耦合，无法通过 DI 灵活替换实现类。

4. 无状态 / 轻量级的类

如果一个类是无状态的（仅包含静态方法，没有实例属性），或实例化成本极低 比如简单的工具类

向量数据库

0 为什么要专门的向量数据库

如果用 MySQL 这类传统数据库存储向量（比如把向量存成字符串 / 数组），会遇到两个无法解决的痛点：

1. 检索速度极慢（暴力计算，无法扩展）

要找相似向量，传统数据库只能做 “暴力遍历”：

  • 对每一个存储的向量，计算它和查询向量的 “距离”（比如余弦相似度）；
  • 如果有 100 万个 768 维向量，就要做 100 万次高维距离计算，单查询可能要几秒甚至几十秒，完全无法满足实时需求（比如用户输入后要快速返回结果）。

2. 无法处理高维数据的 “维度灾难”

向量的维度越高（比如 1000 维以上），传统的索引方式（B + 树、哈希等）完全失效：

  • 高维空间中，“距离” 的意义会变得模糊（所有向量之间的距离都差不多）；
  • 传统数据库没有针对高维向量的优化，存储和计算效率会断崖式下降。

3. 功能缺失

传统数据库没有针对向量的专用功能：比如动态添加 / 删除向量、按相似度排序、批量嵌入、数据持久化优化等，需要自己手写大量代码实现，且效率极低。

向量数据库的核心价值就是 “高效处理相似性检索”，主要体现在：

1. 优化的索引算法（核心）

向量数据库内置了专门的近似最近邻（ANN）算法（比如 HNSW、FAISS、IVF 等），能把 “暴力遍历” 的时间复杂度从 O(n) 降到 O(log n)：

  • 比如 100 万个向量的检索，从几秒缩短到毫秒级；
  • 牺牲极少量的精度（可配置），换取极致的速度，完全满足实时场景。

2. 针对高维向量的存储优化

  • 对向量进行压缩、量化（比如把 32 位浮点数转成 8 位整数），大幅减少存储空间；
  • 优化内存布局，让向量计算更贴合 CPU/GPU 的缓存机制，提升计算效率。

3. 专为向量场景设计的功能

  • 支持批量嵌入（自动把文本转向量并存入）；
  • 支持元数据过滤（比如检索 “水果相关” 且相似度高的向量）；
  • 支持增量更新（动态添加 / 删除向量，无需重建整个索引）；
  • 支持分布式部署（处理亿级向量的大规模场景）。

    1. 高维空间里，*方向差异明显 → 余弦距离特别好用

      语义 embedding 的特点：

      • 向量长度不代表语义，只代表 “强度”
      • 真正决定意思相不相近的是方向

      比如：

      • “我喜欢苹果”
      • “我真的超级超级喜欢苹果”

      两句语义几乎一样，但向量长度可能差很多：

      • 余弦距离：很小（相似）
      • 欧氏距离：很大（不相似）

      👉 余弦会忽略长度，只看语义方向，更符合人的判断。

    2. 地球表面积有限，但你能画出无限多不同的点。

      1. 数学上：方向确实无限

      在 d 维实数空间（比如 768 维）：

      • 方向由单位向量决定
      • 单位向量有 无限多个→ 所以方向无限多

      你随便转一点点角度，就是一个新方向。

      2. 但模型的语义空间：不是真・无限

      模型 embedding 是浮点数，有精度限制：

      • float32 只有 2^32 种可能的数值
      • 768 维向量的不同方向数量是巨大、有限、但远超你能用的

      可以理解成：

      不是数学无限，但对人类工程来说 = 无限够用。

余弦距离 vs 欧氏距离（点积距离）

1. 欧氏距离（你说的 “点几距离”）

衡量两个点在空间里的直线远近。

  • 关心：绝对位置、长度大小
  • 公式：两点直线距离
  • 特点：数值大小很重要，模长不一样，距离就会差很多

2. 余弦距离

衡量两个向量方向的差异，不管长度。

  • 关心：方向、趋势、相似度
  • 公式：1 - 余弦相似度
  • 特点：只看方向，不看长度，模长不影响结果

一句话区别

  • 欧氏距离：看你离我多远。
  • 余弦距离：看咱俩方向一不一样。

举个最直观的例子

用户 A：[1, 2]

用户 B：[2, 4]

用户 C：[3, 1]

  • 欧氏距离：A 和 B 很远，因为数值差一倍。
  • 余弦距离：A 和 B 完全一样，因为方向完全相同。

什么时候用哪个？

  • 文本、embedding、推荐、相似度 → 用 余弦距离
  • 坐标、位置、聚类、物理距离 → 用 欧氏距离

一、简介（优化版）

1.1 什么是 WebSocket

WebSocket 是一种基于 TCP 协议 的全双工通信协议（RFC 6455 标准），用于在 Web 应用与服务器之间建立持久化、双向的实时通信连接。

  • 它先通过 HTTP 协议完成 “协议升级” 握手，成功后脱离 HTTP 协议，在单一 TCP 长连接上实现客户端↔服务器的双向数据传输；
  • 区别于 HTTP 的 “请求 - 响应” 单向模型，WebSocket 允许服务器主动推送数据，无需客户端轮询；

1.2 WebSocket 的优势和劣势（补充完整）

优势（补充落地视角）
  1. 极致实时性：持久化 TCP 连接无需重复建立 / 断开，数据传输延迟可低至毫秒级，远优于轮询（短轮询 / 长轮询）的秒级延迟；
  2. 全双工通信：客户端和服务器可同时、独立地发送数据（如聊天场景中双方实时发消息，无需等待对方请求）；
  3. 大幅降低网络开销：
    • 仅 1 次握手即可建立持久连接，避免 HTTP 轮询的重复请求头（如 Cookie、User-Agent 等）开销；
    • 数据帧体积小（最小帧仅 2 字节），比 HTTP 文本传输更高效；
  4. 兼容 Web 生态：握手阶段基于 HTTP，可穿透大部分防火墙 / 代理服务器，无需额外配置；
  5. 轻量易用：浏览器原生提供 WebSocket API，服务端主流框架（Node.js/Java/Python）均有成熟库支持。
劣势（补充实际痛点）
  1. 兼容性限制：
  2. 服务器资源开销：
    • 每个客户端需维护一个长连接，高并发场景（如百万级在线）会占用大量服务器文件描述符和内存；
    • 需额外处理连接保活、断线重连、心跳检测等逻辑，增加服务端开发复杂度；
  3. 安全风险：
    • 无内置身份校验机制，需业务层实现鉴权（如 Token 验证），否则易被伪造连接；
    • 存在 “WebSocket 劫持” 风险（跨站请求伪造），需通过 Origin 校验、Token 绑定等方式防范；
  4. 调试难度高：
    • 不同于 HTTP 请求可直接在浏览器 Network 面板查看，WebSocket 帧需专用工具（如 Wireshark、浏览器 DevTools 的 WebSocket 面板）调试；
    • 断线后的数据重传、断点续传需业务层自行实现，无原生机制支持。

二 详解

2.2 WebSocket的[生命周期]

WebSocket 生命周期描述了 WebSocket 连接从创建到关闭的过程。一个 WebSocket 连接包含以下四个主要阶段：

  • 连接建立阶段（Connection Establishment）： 在这个阶段，客户端和服务器之间的 WebSocket 连接被建立。客户端发送一个 WebSocket 握手请求，服务器响应一个握手响应，然后连接就被建立了。
  • 连接开放阶段（Connection Open）： 在这个阶段，WebSocket 连接已经建立并开放，客户端和服务器可以在连接上互相发送数据。
  • 连接关闭阶段（Connection Closing）： 在这个阶段，一个 WebSocket 连接即将被关闭。它可以被客户端或服务器发起，通过发送一个关闭帧来关闭连接。
  • 连接关闭完成阶段（Connection Closed）： 在这个阶段，WebSocket 连接已经完全关闭。客户端和服务器之间的任何交互都将无效。

2.3 WebSocket的消息格式

WebSocket 的消息格式与 HTTP 请求和响应的消息格式有所不同。WebSocket 的消息格式可以是文本或二进制数据，并且 WebSocket 消息的传输是在一个已经建立的连接上进行的

WebSocket 消息格式由两个部分组成：消息头和消息体。

消息头包含以下信息：

  • FIN： 表示这是一条完整的消息，一般情况下都是1。
  • RSV1、RSV2、RSV3： 暂时没有使用，一般都是0。
  • Opcode： 表示消息的类型，包括文本消息、二进制消息等。
  • Mask： 表示消息是否加密。
  • Payload length： 表示消息体的长度。
  • Masking key： 仅在消息需要加密时出现，用于对消息进行解密。

消息体就是实际传输的数据，可以是文本或二进制数据。

Depends

  • 预处理（Before）依赖项： 在路由操作函数执行前运行，用于预处理输入数据，验证请求等。
  • 后处理（After）依赖项： 在路由操作函数执行后运行，用于执行一些后处理逻辑，如日志记录、清理等。

安全认证：JWT 与 OAuth2 集成

高级特性：后台任务与 WebSocket

异步后台任务：在 Web 应用中，有些任务可能比较耗时，如发送邮件、记录日志、处理文件等，如果在请求处理过程中同步执行这些任务，会导致响应延迟，影响用户体验。FastAPI 提供了BackgroundTasks来处理这类异步后台任务，让请求能够快速响应，同时在后台执行这些非阻塞任务。

WebSocket 实时通信：WebSocket 是一种在单个 TCP 连接上进行全双工通信的协议，它允许服务器和客户端之间进行实时双向通信。FastAPI 对 WebSocket 提供了良好的支持，使得我们可以方便地开发实时应用，如实时聊天、监控数据推送等。
