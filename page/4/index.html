线程（Thread）

线程是操作系统提供的最小执行调度单位之一，属于进程内部的执行流。

一个进程可以包含多个线程，这些线程共享进程的内存空间，由操作系统进行调度执行。

1. 线程的本质

线程可以理解为：

进程内部的一条执行路径

特点：

  • 由操作系统调度（OS scheduler）
  • 属于内核级并发（kernel-level concurrency）
  • 多线程可以在多核 CPU 上实现并行执行

2. 线程与进程的关系

  • 进程：资源分配单位（内存、文件句柄等）
  • 线程：执行单位（代码执行流）

一个进程中可以包含多个线程：

特点：

  • 线程共享进程内存
  • 线程之间通信简单（但也更容易出错）

3. Python 中的线程

Python 使用 threading 模块支持多线程：

说明：

  • start()：启动线程
  • join()：等待线程结束

4. 线程调度机制

线程由操作系统进行调度：

  • 抢占式调度（preemptive）
  • CPU 时间片轮转
  • 多线程可以“看起来同时运行”

5. Python 线程的限制（GIL）

Python 有一个重要限制：

GIL（Global Interpreter Lock，全局解释器锁）

影响：

  • 同一时刻只能有一个线程执行 Python 字节码
  • 多线程无法真正并行执行 CPU 计算

6. GIL 的影响

✔️ 适合场景（IO 密集）

  • 网络请求
  • 文件读写
  • 数据库操作

原因：

线程在 IO 阻塞时会释放 GIL

❌ 不适合场景（CPU 密集）

  • 图像处理
  • 深度学习计算
  • 大规模数值计算

原因：

线程无法真正并行执行 CPU 计算

7. 线程的优缺点

优点

  • 创建开销比进程小
  • 适合 IO 并发
  • 共享内存，通信方便

缺点

  • GIL 限制并行能力
  • 线程安全问题（竞争条件）
  • 调试复杂

8. 线程 vs 协程 vs 进程（核心对比）

模型 调度方式 并行能力 开销 适用场景
进程 OS调度 强（多核） 高 CPU密集
线程 OS调度 受GIL限制 中 IO并发
协程 用户态调度 无并行 极低 高并发IO

以后怎么避免「误杀整个 loop」

可选改进（当前代码还没做）：

  1. 400 不重试 — retry_if_not_exception_type(BadRequestError) 或只对 429/5xx 重试
  2. run_loop 按轮捕获 — 单轮 run() 失败只打印错误，继续 You>
  3. think() 优雅降级 — API 400 时写 assistant 错误消息并 FINISHED，而不是 raise

核心矛盾

Recovery 的设计是「把错误当作下一轮 user message，让 agent 自我修复」。但 400 schema 错误发生在请求发出之前——只要 bash 还挂在 agent 上，任何一轮都会在 think() 阶段失败，agent 无法调用 patch_file / hot_reload 去修。

所以：坏 schema + 自动 recovery = 必死循环，直到 max_steps 或你 Ctrl+C。

怎么打破循环（手动）

  1. 重启进程，并修正 bash.py（properties 改回正确结构）
  2. 或在代码里先 卸载 bash：available_tools 里移除 bash，再跑
  3. 修好后 hot_reload + remount_tools=["bash"]

框架上还应补的防护（如需我可以改）

  1. 同一 error fingerprint 最多 recovery 1–2 次，之后停掉并回到 You>
  2. 新 run() 开始时 current_step = 0、state = IDLE
  3. schema 类 400：不 schedule recovery，或自动 unmount 报错工具
  4. BaseTool.to_params() 校验 parameters.type == "object"，坏 schema 不发给 API

一句话：你故意写错的 schema 导致每次 LLM 调用必 400；recovery 又把失败自动当成下一轮 request，而 bad tool 仍挂着，所以会在同一 session 里无限重试，直到 step 上限或你手动停。这不是 API「随机报错」，是预期内的死循环。

框架防护实现方案

1. 静态防线：BaseTool.to_params() 强制校验（源头拦截）

别让脏数据出门。在工具加载或序列化为 OpenAI JSON Schema 时，直接在本地做拦截。如果格式不对，拒绝启动或拒绝发送。

2. 动态防线：Schema 400 自动隔离/卸载（Unmount）

如果静态校验漏过了，API 返回了 400（且特征明显是 Schema 错误），框架应该启动隔离机制——“既然你让我过敏，我就先把你切除”。

2.3 那为什么tool 设计成tool…execute

Task 本质是“调度描述”，它的存在是为了让系统可以把“什么时候做什么事”持久化下来、排队、恢复、分布式执行。它更像一条记录、一份计划书，所以它必须保持稳定、纯粹、无依赖，这样才能被存到数据库里、跨进程传输、失败后重新执行。如果你让 Task 自己去 execute，那它就必须知道怎么调用 LLM、怎么用 tool、怎么处理 retry、怎么管理状态，这**会导致它从“数据”变成“运行时系统”，**整个调度层会和业务逻辑强耦合，系统会逐渐失去可拆分性和可扩展性。

而 Tool 不一样，Tool 本质是“能力本身”，它不是计划，也不是调度结果，而是最底层的动作单元，比如搜索、计算、请求 API、读数据库。它的特点是输入明确、输出明确、无调度逻辑，它不会关心什么时候被调用，也不会关心是谁在调用，它只负责“做一件事”。所以 Tool 设计成 execute 是合理的，因为它本来就是被执行的对象。

真正关键的区别在于：
Task 解决的是“要不要做、什么时候做”，Tool 解决的是“具体怎么做”。

如果把 Task 也设计成 execute，就等于把调度系统和执行系统混在一个对象里，最终会变成一个既要管时间、状态、队列，又要懂业务逻辑和外部能力的“超级对象”，系统会失去分层结构，后期扩展（比如加新 tool、加分布式 worker、加重试队列）都会变得非常痛苦。

所以不是“能不能这样设计”的问题，而是：
一旦 Task 负责 execute，系统就不再是调度系统，而变成一个难以拆分的运行时整体；而把 execute 放在 Tool 上，是在保持“调度”和“能力”分离，让整个系统可以像操作系统一样分层运行。

Tool 和 Task / Executor 根本不是同一层抽象

1 *, 和 **kwargs: Any 的区别是什么 作用是什么?

在 Python 函数签名里，这两个东西作用不同：

  • *,：把它后面的参数都变成只能用关键字传（keyword-only）。

    • 所以这里 agent_id、parent_id 不能用位置参数传，只能写成 agent_id="..."、parent_id="..."。

  • **kwargs: Any：收集调用时额外传入的、签名里没显式列出来的所有关键字参数，打包成一个 dict（类型标注为值是 Any）。

    • 在 runtime 里通常用来把这些“创建 agent 的参数”（比如 name、system_prompt、max_steps 等）继续转发给工厂/agent 构造。

​ 在 Eye-to-Hand 的问题下，待求量为相机到机械手基座坐标系的固定转换矩阵 。考虑到相机是固定在一个位置，因此相机只有相对于基座坐标系才是固定不变的，这样我们的待求量 是一个固定的参数，这样的标定才是有意义的。

2 问题汇总

2.1 在手眼标定中，棋盘格是否需要确认上下方向?

通常不需要刻意确认“上下方向”，但必须保证棋盘格在标定过程中相对于所附着的刚体（末端或固定支架）保持固定的位姿。

2.2 眼在手上标定时，移动的是机器人末端（夹爪/法兰），棋盘格必须保持固定不动。

手眼标定的核心方程 AX=XBA**X=XB 或等价形式依赖于相对运动的约束：

  • AA：机器人末端的两次运动之间的变换（由机器人控制器给出）
  • BB：相机相对于同一标定板的两次观测之间的变换（通过视觉求解）

如果棋盘格也在移动，那么两次观测之间的 BB 就不再是单纯的相机运动，而是相机与棋盘格相对运动的叠加。此时方程退化为 AX=X⋅(未知移动棋盘格的影响)A**X=X⋅(未知移动棋盘格的影响)，无法分离出唯一的手眼矩阵 XX。

2.3 是否需要拍全棋盘格?

必须确保棋盘格的所有内角点都完整出现在相机视野内。

OpenCV 的 cv2.findChessboardCorners 要求棋盘格的所有内角点（例如 9×6 棋盘格有 8×5 个内角点）都在图像中，且能够形成完整的矩形网格。

  • 如果棋盘格部分超出视野或被遮挡，函数会返回 False，无法提取任何角点。

  • 即使强行使用部分角点（修改代码），也无法确定角点的全局编号（哪个是(0,0)哪个是(8,5)），导致物体坐标系错乱。

2.4 图像xyz和法兰的xyz不一样,标定有影响吗?

没有影响。手眼标定本身就包含了两个坐标系之间的旋转对齐，不需要你事先将相机XYZ与法兰XYZ对齐。标定结果会自然地描述两个坐标系之间的相对方位

2.5 位姿坐标如何选择? 选谁的位姿坐标?

注意! 位姿要选择和相机相对静止的坐标

需要选择和手上相机固定轴的坐标, 如果相机固定在末端轴, 就需要末端的位姿; 如果机械臂末端而外嫁了工具坐标, 且相机固定在工具上, 那么位姿输入要是根据坐标而不是末端坐标
