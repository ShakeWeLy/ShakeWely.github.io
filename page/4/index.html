7 loop

以后怎么避免「误杀整个 loop」

可选改进（当前代码还没做）：

  1. 400 不重试 — retry_if_not_exception_type(BadRequestError) 或只对 429/5xx 重试
  2. run_loop 按轮捕获 — 单轮 run() 失败只打印错误，继续 You>
  3. think() 优雅降级 — API 400 时写 assistant 错误消息并 FINISHED，而不是 raise

核心矛盾

Recovery 的设计是「把错误当作下一轮 user message，让 agent 自我修复」。但 400 schema 错误发生在请求发出之前——只要 bash 还挂在 agent 上，任何一轮都会在 think() 阶段失败，agent 无法调用 patch_file / hot_reload 去修。

所以：坏 schema + 自动 recovery = 必死循环，直到 max_steps 或你 Ctrl+C。

怎么打破循环（手动）

  1. 重启进程，并修正 bash.py（properties 改回正确结构）
  2. 或在代码里先 卸载 bash：available_tools 里移除 bash，再跑
  3. 修好后 hot_reload + remount_tools=["bash"]

框架上还应补的防护（如需我可以改）

  1. 同一 error fingerprint 最多 recovery 1–2 次，之后停掉并回到 You>
  2. 新 run() 开始时 current_step = 0、state = IDLE
  3. schema 类 400：不 schedule recovery，或自动 unmount 报错工具
  4. BaseTool.to_params() 校验 parameters.type == "object"，坏 schema 不发给 API

一句话：你故意写错的 schema 导致每次 LLM 调用必 400；recovery 又把失败自动当成下一轮 request，而 bad tool 仍挂着，所以会在同一 session 里无限重试，直到 step 上限或你手动停。这不是 API「随机报错」，是预期内的死循环。

框架防护实现方案

1. 静态防线：BaseTool.to_params() 强制校验（源头拦截）

别让脏数据出门。在工具加载或序列化为 OpenAI JSON Schema 时，直接在本地做拦截。如果格式不对，拒绝启动或拒绝发送。

2. 动态防线：Schema 400 自动隔离/卸载（Unmount）

如果静态校验漏过了，API 返回了 400（且特征明显是 Schema 错误），框架应该启动隔离机制——“既然你让我过敏，我就先把你切除”。

11 进行工具管理?

🎯 动态工具检索 (Two-Stage Tool Retrieval)

不要把所有的工具一次性塞给大模型。

  1. 第一阶段（检索）： 用户输入请求后，利用一个轻量级的向量检索器（Embedding Router）或意图分类模型，从数百个工具中筛选出最相关的 3~5 个工具。
  2. 第二阶段（决策）： 仅将这几个筛选后的工具 Schema 送入大模型，让其进行最终的调用决策。这不仅极大地节省了 Context 成本，还显著提高了 Agent 的决策准确率。

动态注入： 不同任务类型使用不同的工具子集。例如：

  • 编程任务 → 重点注入代码、文件、调试工具
  • 研究任务 → 重点注入搜索、浏览、RAG 工具

999 自我进化

自我进化用一句来讲，大概是这样：

真实任务里的经验，怎么变成下一次任务可复用、可验证、可治理的能力。

策略

上下文进化：将执行经验、用户偏好或环境约束写回本地记忆文件、会话索引或技能目录，在下一次任务触发时通过检索提取并拼接入上下文。

2.3 那为什么tool 设计成tool…execute

Task 本质是“调度描述”，它的存在是为了让系统可以把“什么时候做什么事”持久化下来、排队、恢复、分布式执行。它更像一条记录、一份计划书，所以它必须保持稳定、纯粹、无依赖，这样才能被存到数据库里、跨进程传输、失败后重新执行。如果你让 Task 自己去 execute，那它就必须知道怎么调用 LLM、怎么用 tool、怎么处理 retry、怎么管理状态，这**会导致它从“数据”变成“运行时系统”，**整个调度层会和业务逻辑强耦合，系统会逐渐失去可拆分性和可扩展性。

真正关键的区别在于：
Task 解决的是“要不要做、什么时候做”，Tool 解决的是“具体怎么做”。

如果把 Task 也设计成 execute，就等于把调度系统和执行系统混在一个对象里，最终会变成一个既要管时间、状态、队列，又要懂业务逻辑和外部能力的“超级对象”，系统会失去分层结构，后期扩展（比如加新 tool、加分布式 worker、加重试队列）都会变得非常痛苦。

在 Python 函数签名里，这两个东西作用不同：

    • 在 runtime 里通常用来把这些“创建 agent 的参数”（比如 name、system_prompt、max_steps 等）继续转发给工厂/agent 构造。

2 问题汇总

2.1 在手眼标定中，棋盘格是否需要确认上下方向?

通常不需要刻意确认“上下方向”，但必须保证棋盘格在标定过程中相对于所附着的刚体（末端或固定支架）保持固定的位姿。

2.2 眼在手上标定时，移动的是机器人末端（夹爪/法兰），棋盘格必须保持固定不动。

手眼标定的核心方程 AX=XBA**X=XB 或等价形式依赖于相对运动的约束：

  • AA：机器人末端的两次运动之间的变换（由机器人控制器给出）
  • BB：相机相对于同一标定板的两次观测之间的变换（通过视觉求解）

如果棋盘格也在移动，那么两次观测之间的 BB 就不再是单纯的相机运动，而是相机与棋盘格相对运动的叠加。此时方程退化为 AX=X⋅(未知移动棋盘格的影响)A**X=X⋅(未知移动棋盘格的影响)，无法分离出唯一的手眼矩阵 XX。

2.3 是否需要拍全棋盘格?

必须确保棋盘格的所有内角点都完整出现在相机视野内。

OpenCV 的 cv2.findChessboardCorners 要求棋盘格的所有内角点（例如 9×6 棋盘格有 8×5 个内角点）都在图像中，且能够形成完整的矩形网格。

  • 如果棋盘格部分超出视野或被遮挡，函数会返回 False，无法提取任何角点。

5.1 Why multi-agent?

When developers say they need “multi-agent,” they’re usually looking for one or more of these capabilities:

  • Context management: Provide specialized knowledge without overwhelming the model’s context window. If context were infinite and latency zero, you could dump all knowledge into a single prompt—but since it’s not, you need patterns to selectively surface relevant information.
  • Distributed development: Allow different teams to develop and maintain capabilities independently, composing them into a larger system with clear boundaries.
  • Parallelization: Spawn specialized workers for subtasks and execute them concurrently for faster results.

Patterns

Here are the main patterns for building multi-agent systems, each suited to different use cases:

Pattern How it works
Subagents A main agent coordinates subagents as tools. All routing passes through the main agent, which decides when and how to invoke each subagent.
Handoffs Behavior changes dynamically based on state. Tool calls update a state variable that triggers routing or configuration changes, switching agents or adjusting the current agent’s tools and prompt.
Skills Specialized prompts and knowledge loaded on-demand. A single agent stays in control while loading context from skills as needed.
Router A routing step classifies input and directs it to one or more specialized agents. Results are synthesized into a combined response.
Custom workflow Build bespoke execution flows with LangGraph, mixing deterministic logic and agentic behavior. Embed other patterns as nodes in your workflow.

  • 2. token → id（映射到词表索引）

    • 每个 token 对应词表中的一个整数编号，形成 input_ids：
      • encoded_input["input_ids"] 是一个二维张量：[batch_size, seq_len]。

  • 3. 生成 attention_mask（哪些位置是真实内容，哪些是 padding）

    • 由于你设置了 padding=True，不同长度的句子会填充到同样的 seq_len。
    • attention_mask 用 1/0 标记：
      • 1：真实 token 位置
      • 0：补上的 padding 位置
    • 后面在 mean_pooling 里就是用这个 mask 来“只对真实 token 求平均”。

  • 4. 生成 token_type_ids（区分句子 A/B，用于部分模型）

    • 对于单句输入，通常全 0；
    • 对于句对任务（如句子对分类），可以用 0/1 区分哪部分是第一句、哪部分是第二句。
    • 你这里只是单句列表，所以主要是兼容模型接口，实际不会特别用到它。

总结一句话：
tokenizer 把原始中文句子变成模型能吃的“数字化输入”（input_ids + attention_mask + token_type_ids），然后模型再基于这些数字算出每个 token 的向量，最后你用 mean_pooling 把它们汇成句向量。

2.2.1 为什么拆分成一个个关键信息点?

向量嵌入（embedding）确实是基于“语义”的，但“语义”并不是你想象中那种“越长越自然越好”的完整段落。 这正是很多人对 embedding 的最大误解。

让我用最直白的方式解释为什么我们要把文本“拆分成一个个关键信息点”（或结构化、精炼成短句/关键词列表），而不是直接扔整段长文本：

1. 向量模型的实际工作原理（不是魔法）

  • Embedding 模型（如你现在用的那个）会把输入文本切成 token（词或子词），然后计算每个 token 的重要性，并生成一个固定维度的向量。

  • 它的目标是：让语义相近的内容在向量空间里距离更近。

  • 但模型

    注意力是有限的

    （尤其是上下文长度限制在 512~8192 token 的模型）。如果输入文本又臭又长、充满重复和废话，它就会：

    • 把注意力分散到无关的高频词上（比如“dripping wet”“musky aroma”“4.47 rating”“guaranteed to find the perfect”等营销废话）。
    • 核心语义（“学校”“女学生”“女教師”“无限制插入”“定額挿れ放題”）被稀释，导致向量不够“尖锐”。

结果就是：两个真正相关的 JAV 作品，向量相似度反而低；而一些标题里堆了很多通用色情词的无关作品，反而分数更高。
