为什么需要KV Cache？

https://www.zhihu.com/question/653658936/answer/107469197025

在自回归生成中，每个新Token的生成都需要所有历史Token的Key和Value。如果每次重新计算所有历史Token的K和V，计算量随序列长度二次增长 O(N2)。

KV Cache的核心思想：用显存换计算——将之前计算好的K和V存储起来，新Token生成时只需计算当前Token的K和V，然后从Cache中读取历史K和V。

因为k和v是会在每一个新的q中重复使用, 但是q会变:推理过程中, 之前的q和kv的结果会cache, 但是之前的q不会, 而之前kv因为要和新的q计算, 所以就需要cache

❌ 1. 为什么“之前计算的结果”无法被 Cache？(图片红色框)

你可能觉得，既然 Q4Q_4Q4​ 和 K1..K4K_1..K_4K1​..K4​ 已经算过一次注意力权重了，下一次 Q5Q_5Q5​ 进来时，能不能复用一部分之前算出来的权重（结果）？

答案是：不能。因为每一轮的“总权重”必须重新做 Softmax 归一化。

我们用数字做个极简的对比：

  • 这一轮（生成第 5 个字）： 我们拿 Q4Q_4Q4​ 去和 K1..K4K_1..K_4K1​..K4​ 算点积，假设算出来的原始得分是 [10,5,2,8][10, 5, 2, 8][10,5,2,8]。

    新来的主角是 Q5Q_5Q5​（代表第 5 个字“改”）。

    Q5Q_5Q5​ 是一个全新的向量，它去和 K1..K5K_1..K_5K1​..K5​ 算点积。算出来的原始得分可能是 [1,9,4,2,12][1, 9, 4, 2, 12][1,9,4,2,12]。

⚙️ 内部加工过程（Layer 内部发生了什么？）

当 XinX_{in}Xin​ 进入第 NNN 层后，会发生以下两步关键转换：

第一步：Self-Attention 空间整合（横向互动）

  1. 模型利用权重矩阵把 XinX_{in}Xin​ 投影出我们上一问提到的 Q,K,VQ, K, VQ,K,V。
  2. 核心动作： 拿着当前 Token 的 QQQ，去和历史所有 Token 的 KKK 做点积，算权重，然后对 VVV 加权求和。
  3. 结果： 这一步实现了“信息在不同 Token 之间的横向流动”。比如“工”字在这一步融合了“人”字的信息。

第二步：FFN / MLP 维度特征提取（纵向挖掘）

  1. 经过注意力机制融合后的向量，会进入一个前馈神经网络（通常是一个两层的全连接层）。
  2. 核心动作： 此时 Token 之间不再互相关注了，而是每个 Token 各自独立地进行非线性变换。它把维度放大（比如从 4096 升到 11008 维），再缩小回来。
  3. 结果： 这一步用来记忆知识、抽取高阶特征（类似专家系统在深度剖析这个词当前代表的含义）。

🔹 每一层的输出（Output Matrix：XoutX_{out}Xout​）

  • 数学形式： 形状与输入完全一致，依然是 [Batch_Size, Sequence_Length, Hidden_Dim]。
  • 语义内涵： * 经过当前层的“横向融合（Attention）”和“纵向深挖（FFN）”后，每个 Token 位置上的向量被赋予了更新、更抽象、更深刻的上下文语义。
    • 这个 XoutX_{out}Xout​ 随即作为 XinX_{in}Xin​，毫无保留地送入第 N+1N+1N+1 层。

3 上下文窗口

🧭 上下文窗口长度的决定因素

所以，你问的“上下文窗口的长度就是这个的运行因素吗？”答案是绝对的“是”。大模型厂商宣称的“支持 100k 还是 1M 上下文”，本质上是在向这两个极限发起挑战。

为了让上下文窗口变得极长，技术界在 2024~2026 年间普及了以下几种续命技术：

  1. GQA（Grouped-Query Attention，分组查询注意力）：

    让多个不同的 QQQ 共享同一个 KKK 和 VVV。这样可以把 KV Cache 的体积直接压缩到原来的 1/41/41/4 甚至 1/81/81/8，大大缓解了显存压力。

  2. PagedAttention（如 vLLM 框架）：

    像操作系统的虚拟内存一样，把显存切成一块块小碎块（Pages）来动态管理 KV Cache。不再为每个请求预留连续的巨大显存，解决了显存碎片化问题，让吞吐量提升数倍。

  3. RoPE（旋转位置编码）的外推与插值：

    不仅要显存放得下，还要模型在面对第 100,000 个位置的词时，数学上不会“算糊涂”。科学家们通过修改位置编码的数学公式，让模型能理解超长距离的位置依赖。

4 串行工程优化

5 PagedAttention

🪨 1. 传统 KV Cache 的痛点：巨大的显存浪费

在传统的推理框架中，模型必须为每一个请求（Request）在显存中开辟一块连续的物理空间，用来存放该请求源源不断产生的 KV Cache。

因为模型在生成前根本不知道用户最终会生成多长的文本（比如可能生成 10 个字，也可能生成 2048 个字），为了防止中途显存溢出，传统的做法是按照最大长度（Max Sequence Length）预先分配一整块连续显存。

这就导致了三个极其致命的显存浪费（通常浪费高达 60% - 80%）：

  1. 未用预留浪费（Reservation）： 如果模型为用户预留了 2048 个 Token 的空间，但用户聊了 10 个字就结束了，剩下的 2038 个 Token 空间的显存就被白白浪费了，别人也用不了。
  2. 动态成长浪费（Internal Fragmentation）： 随着文本一步步生成，显存从前往后慢慢填满，那些还没用到的空间只能空置。
  3. 内存碎片（External Fragmentation）： 不同的请求频繁启动和结束，显存被切割得支离破碎，明明总剩余显存还够，却因为找不到一块连续的显存，导致新请求无法启动。

💡 2. PagedAttention 的降维打击：像操作系统一样分页

PagedAttention 的核心思想是：打破“连续性”的诅咒。

它允许将每个请求的 KV Cache 存放在不连续的物理显存中。

核心机制：物理块（Physical Blocks）与虚拟映射

  1. KV 块（KV Blocks）： PagedAttention 把每个请求的 KV Cache 划分为固定大小的“块”（Block），每个块默认可以容纳固定数量（例如 16 个）Token 的 KV 向量。
  2. 逻辑内存 vs 物理内存：
    • 逻辑块（Logical Blocks）： 在模型眼里，它看到的依然是连续的一串字（Block 0: 0~15字 →\rightarrow→ Block 1: 16~31字 →\rightarrow→ Block 2: 32~47字）。
    • 物理块（Physical Blocks）： 在实际的显卡内存里，这些块被分散在天南海北、任意不连续的空闲位置。
  3. 块表（Block Table）： 框架维护了一个映射表（类似操作系统的页表 Page Table）。当模型需要计算第 35 个字的 Attention 时，它通过块表查到逻辑上的 Block 2 对应的物理显存地址是 Physical Block 104，然后直接去那里读取数据。

KV cache量化

4. 主流的 KV Cache 量化技术方案

为了解决精度损失问题，业界演进出了几种不同的量化粒度：

① 按 Token 量化（Per-Token Quantization）

  • 原理：对每一个 Token 向量，独立计算一组缩放因子 SSS。
  • 特点：实现简单，对吞吐量友好，但在面对离群值通道时，精度保护不够。

② 按通道/按头量化（Per-Channel / Per-Head Quantization）

  • 原理：针对 K,VK, VK,V 矩阵的不同维度（如每个 Attention Head 内部的 Channel）分别计算缩放因子。
  • 特点：精度保留极好，能完美避开离群值的干扰，但硬件计算对齐稍微复杂一点。

③ FP8 KV Cache（Hopper / Blackwell 架构新宠）

随着 NVIDIA H100 等新一代 GPU 硬件原生支持 FP8（8位浮点数，如 E4M3 和 E5M2 格式），FP8 KV Cache 正在迅速取代 INT8。

  • 优势：它既有低精度的带宽优势，又保留了浮点数对大范围数值（离群值）的容忍度。在 vLLM 等主流框架中，开启 FP8 KV Cache 几乎可以做到几乎无损的精度保留。

④ 极致压缩：INT4 量化（如 KIVI 算法）

2024 年底至 2026 年，像 KIVI 这样的算法把 KV Cache 卷到了 INT4。

  • 核心思路：因为 KKK 向量对离群值极度敏感，而 VVV 向量相对平缓。KIVI 对 KKK 采用 Group-wise 细粒度量化，对 VVV 采用 Channel-wise 量化。在 Llama 等模型上，成功在 4-bit 精度下实现了近乎无损的超长文本生成。

3. 为什么这样可以实现？（关键逻辑）

你可能会问：共享了 K 和 V，模型不会变笨吗？

研究发现：

  1. 信息的冗余性： 在 Transformer 中，不同头捕捉到的特征往往高度重合。让多个头共享 KV，损失的信息量远小于节省的显存带来的收益。
  2. Q 的多样性保留： 因为 HqH_qHq​（查询头）的数量依然保持为 32 个，每一个“查询者”依然拥有独特的视角去理解问题。只要“查询者”足够多，模型就依然能捕捉到细微的语义差别。

1 前缀和算法

没关系，前缀和（Scan）算法第一次看确实容易绕晕，因为它和我们习惯的串行思维完全不同。

我们用一个最接地气的排队买票例子，彻底拆解它的原理。

什么是前缀和？（用买票类比）

假设有 4 个人排队买电影票，每个人想买的张数不一样：

  • 输入数组 AAA：[2, 3, 1, 4] （分别代表甲、乙、丙、丁要买的票数）

现在我们要计算每个人排队时，在自己之前，前面一共卖出了多少张票。这样大家就能知道自己买完票后，票根上的序号是多少。

  • 独占式前缀和（Exclusive Scan）：不包含自己，只算前面的人。
    • 甲前面没人 →\rightarrow→ 0
    • 乙前面有甲 →\rightarrow→ 2
    • 丙前面有甲+乙 →\rightarrow→ 2+3=2 + 3 =2+3= 5
    • 丁前面有甲+乙+丙 →\rightarrow→ 2+3+1=2 + 3 + 1 =2+3+1= 6
    • 输出数组 BBB：[0, 2, 5, 6]

在 CPU 里，我们用一个 for 循环，一边走一边累加，一眨眼就建好了。但是在 GPU 里，有几千个线程同时在跑，它们不能像排队一样“一个接一个”地去加，否则并行就变成了串行。

那 GPU 怎么同时算出这个结果呢？这就需要用到 Blelloch 算法。

GPU 的并行解法：Blelloch 算法

为了让成百上千个线程同时干活，算法把过程分成了两步：上划阶段（算总和） 和 下划阶段（发结果）。

我们以 8 个数字 [3, 1, 7, 0, 4, 1, 6, 3] 为例：

第一步：Up-Sweep（上划阶段）—— 画一棵倒过来的树

这一步的目的和“归约”一样，把数据两两相加，一层一层往上报，直到算出总和。

  • 第一层：两两相加
    • 3+1=43+1=\mathbf{4}3+1=4
    • 7+0=77+0=\mathbf{7}7+0=7
    • 4+1=54+1=\mathbf{5}4+1=5
    • 6+3=96+3=\mathbf{9}6+3=9
    • 现在的数组变成：[3, 4, 7, 7, 4, 5, 6, 9]（加粗的位置更新了）
  • 第二层：跨步增大，继续两两相加
    • 4+7=114+7=\mathbf{11}4+7=11
    • 5+9=145+9=\mathbf{14}5+9=14
  • 第三层：最后一加
    • 11+14=2511+14=\mathbf{25}11+14=25（这是整个数组的总和）

此时，数组的最后一个位置变成了 25。

第二步：Down-Sweep（下划阶段）—— 把结果分发下去

这是最巧妙的一步。我们先把顶端的总和清零（变成 0），然后从上往下走。

每遇到一个节点，做两件事：

  1. 把自己的值传给左子节点。
  2. 把自己原来的值和左子节点的值相加，传给右子节点。

我们来看看这个神奇的过程：

  • 顶层：把最后的 25 变成 0。
  • 往下走第一层：
    • 原来左边是 11，右边是 14。
    • 按照规则：旧的 0 给左边；左边的 11 加上旧的 0 变成 11 给右边。
    • 现在的顶层两节点变成：[11, 0] （对应原来的 11 和 14 位置）。
  • 继续往下走：重复这个“左传，加右”的操作。

当这个过程一直推导到最底层时，你会发现，原本的数组魔术般地变成了：

这就是原数组 [3, 1, 7, 0, 4, 1, 6, 3] 的独占前缀和！

  • 第 0 个数前面总和是 0
  • 第 1 个数前面总和是 3
  • 第 2 个数前面总和是 3+1=43+1 = \mathbf{4}3+1=4
  • 第 3 个数前面总和是 3+1+7=113+1+7 = \mathbf{11}3+1+7=11
  • ……以此类推。

为什么要大费周章这么做？

你可能会问：“又是上划又是下划，这不比 CPU 的 for 循环复杂多了吗？”

对单线程来说是的。但对 GPU 来说：

  1. 树的每一层，所有节点都是并行计算的。原本需要 NNN 次的串行相加，现在只需要 log⁡2N\log_2 Nlog2​N 层的计算。
  2. 处理 100 万个数据，CPU 的 for 循环要走 100 万步；而 GPU 只需要上划 20 层，下划 20 层，总共 40 步就能搞定。

总结

  • 前缀和就是求“当前元素之前所有元素的累加和”。
  • GPU 不能用 for 循环硬干，所以用树状结构。
  • Up-Sweep 像拼图一样把局部和合并上去。
  • Down-Sweep 利用“左传、加右”的数学规律把偏移量完美分发下来。

1. 核心概念：什么是“双调序列”？

在学算法之前，先记住一个定义：

双调序列（Bitonic Sequence）：一个数组，它满足先单调递增，后单调递减（或者先递减后递增）。它就像一座“山峰”或者一个“山谷”。

  • 比如 [1, 4, 9, 8, 5, 2] 就是一个标准的双调序列（先升到 9，再降到 2）。
  • 甚至把这个序列循环位移，比如 [5, 2, 1, 4, 9, 8]（先降到 1，再升到 9），它依然算双调序列。

为什么双调序列这么重要？

因为数学家 Batcher 证明了一个定理（双调合并定理）：

如果你把一个双调序列对半分开，让前半部分的每一个元素和后半部分对应位置的元素进行比较（小的放前面，大的放后面），那么：

  1. 得到的前半部分和后半部分，各自依然是双调序列。
  2. 前半部分的所有元素，都绝对小于后半部分的所有元素。

这就太厉害了！这意味着只要数据变成了“双调序列”，GPU 只需要无脑地对半分、两两比较，就能把数据切成“小的一堆”和“大的一堆”，一直切下去，整个数组就排好序了。这个过程叫做 Bitonic Merge（双调合并）。

2. 核心矛盾：现实数据不是双调的怎么办？

你肯定会问：“人家给我的初始数组是乱序的（比如 [4, 2, 7, 1]），根本不是什么先升后降的山峰，怎么用这个定理呢？”

双调排序的精妙解法：农村包围城市，从小山峰拼成大山峰！

  • 2 个元素：任意两个数，一定能组成一个双调序列（一个升，一个降，或者直接看作双调）。
  • 第 1 阶段（制造小山峰）：把每 2 个元素排成一升一降。比如 [4, 2] 变成升序 [2, 4]，[7, 1] 变成降序 [7, 1]。拼起来就是 [2, 4, 7, 1]。看！这不就组成了长度为 4 的“先升后降”的双调小山峰了吗？
  • 第 2 阶段（制造中山峰）：对这个长度为 4 的双调序列进行“双调合并”，把它变成一个长度为 4 的纯升序序列。同时把隔壁 4 个元素变成纯降序序列。两边一拼，又变成了一个长度为 8 的双调大山峰！
  • 最终阶段：当全班 100 万个数据变成了一座超级大山峰时，执行最后一次总合并，全变成升序，大功告成！

3. 图解执行过程（以 8 个数字为例）

我们来看看乱序数组 [3, 7, 4, 8, 6, 2, 1, 5] 是如何一步步被驯服的。

双调排序要求数组长度必须是 2n2^n2n。

阶段一：两两成组，构建长度为 4 的双调序列

  • 线程同时干活：
    • 把前两个 [3, 7] 变成升序 →\rightarrow→ [3, 7]
    • 把次两个 [4, 8] 变成降序 →\rightarrow→ [8, 4]
  • 此时前 4 个数合并成了 [3, 7, 8, 4]（完美的山峰：3到8升，8到4降）。
  • 同理，后 4 个数 [6, 2, 1, 5] 经过一升一降的处理，变成了 [2, 6, 5, 1]（也是完美的山峰）。

阶段二：四四成组，构建长度为 8 的双调序列

现在我们手头有两个长度为 4 的双调山峰了。

  • 左边 4 个数 [3, 7, 8, 4]：我们要把它合并成一个纯升序序列。
    • 根据刚才的定理，跨步为 2 对半分比较：3和8比，7和4比。
    • 经过两轮无脑两两比较，它变成了纯升序：[3, 4, 7, 8]。
  • 右边 4 个数 [2, 6, 5, 1]：我们要把它合并成一个纯降序序列。
    • 经过无脑两两比较，它变成了纯降序：[6, 5, 2, 1]。
  • 合龙！ 现在把左边（升）和右边（降）拼起来：[3, 4, 7, 8, 6, 5, 2, 1]。
  • 看奇迹！ 整个 8 个数字的数组，现在变成了一座覆盖全体的、完美的、先升后降的超级大山峰！

阶段三：终极大合并（Bitonic Merge）

既然全数组已经是一座大山峰了，我们只需要对它进行最后的折半清洗：

  1. 跨步为 4 比较（0和4比，1和5比…）：小的放左，大的放右。
    • 数组变成：[3, 4, 2, 1 | 6, 5, 7, 8] （左边全部小于右边！）
  2. 跨步为 2 比较：
    • 数组变成：[2, 1, 3, 4 | 6, 5, 7, 8]
  3. 跨步为 1 比较（相邻比较）：
    • 数组变成：[1, 2, 3, 4 | 5, 6, 7, 8]

全部排好序了！

4. 为什么它是 GPU 的最爱？

看完过程，你发现规律了吗？

  1. 没有任何未知的跳转：第几步该哪个位置和哪个位置比，在数组长度确定的那一刻就固定了。
  2. 完美并行：每一轮比较中，所有的两两比较都是互相独立的！比如 0和4比 的时候，1和5比 可以在另一个线程同时进行，不需要等待。
  3. 硬件友好：当跨步很小（比如在 32 以内）时，所有的比较和交换都可以通过 Warp Shuffle（线程束洗牌指令） 直接在寄存器里完成，根本不需要读写昂贵的内存。

线程束（Warp）在执行两条指令之间平均要等 33.1 个周期，其中有 19.7 个周期（高达 59.6%） 卡在了等待 MIO（Memory Input/Output）指令队列释放空间上。说明 MIO 管道被塞满了。

现状数据： 某些 L2 Slices（分片）的活跃周期比平均值高出了 40.09%，而最闲的分片比平均值低 3.95%。

诱因：

  1. 非连续/固定步长的内存访问（Strided Access with Power-of-2 Steps）： 如果你的线程在访问一个大矩阵或多维数组时，跳跃的步长（Stride）刚好是 2 的幂次方（例如每次跳跃 1024、2048 个元素，这在处理图像通道、矩阵转置、或者特定 ROI 区域拉取时非常常见）。这会导致所有线程计算出来的物理内存地址，经过哈希后全部神奇地指向同一个或少数几个 L2 Slice。
  2. 严重的内存热点（Data Hotspots）： 大量的线程在同一时间去读取/原子写入（Atomic Operations）全局显存中的同一块特定区域（比如全局计数器、或者某个特定的锚点数据）。

4 Thread Divergence（线程分支分歧）

1. 现象解读：一半的算力在“陪跑”

  • 核心数据： 该 Kernel 在执行时，每个周期平均只有 16.1 个线程是真正活跃（Active）的。
  • 直白翻译： GPU 是以 Warp（线程束，共 32 个线程） 为最小单位由硬件同步执行相同指令的（SIMT 架构）。而你的程序在运行时，一个 Warp 里的 32 个兄弟，平均每个周期只有 16.1 个在真正干活，剩下的 15.9 个线程都在围观或被挂起。你的 GPU 算力直接被白白浪费了近 50%。

2. 为什么会发生 Thread Divergence？

根本原因在于你的 CUDA 代码中包含了条件分支语句（如 if-else、switch、while），并且分选条件取决于线程的 ID 或它处理的数据。

当一个 Warp 内的 32 个线程走到一个 if-else 冲突点时：

  1. 满足 if 条件的线程（假设有 16 个）去执行 if 块内的代码，此时不满足条件的另外 16 个线程必须原地原地挂起、死等。
  2. if 块执行完后，轮到满足 else 条件的 16 个线程去执行，此时刚才干完活的 16 个线程反过来原地死等。
  3. 这种串行排队执行不同分支的现象，就是分支分歧

5 Long Scoreboard Stalls（长记分板停顿）

  • 核心数据： 线程束（Warp）在两条指令之间平均要等 40 个周期，其中有 30.3 个周期（高达 75.7%） 都卡在 Long Scoreboard 依赖上。
  • 什么是 Long Scoreboard？ GPU 的“记分板（Scoreboard）”是用来追踪指令数据依赖的硬件机制。而 Long Scoreboard 专门负责追踪高延迟的内存访问请求——主要包括：从全局显存（Global Memory）、本地内存（Local Memory）以及纹理内存（Texture）中读取数据。
  • 现状解读： 你的代码发出了读取显存的指令，但数据从**遥远的 DRAM 运回片上寄存器需要几百个周期。**在这期间，后续的代码又马上需要用到这个数据。硬件一看数据还没到，只能让线程束原地“发呆”死等。

6 Achieved Occupancy（实际占用率偏低）

  • 核心数据： 理论最大占用率是 100%，但实际测得的占用率（Achieved Occupancy）只有 74.4%。
  • 为什么会有这个落差？ 理论占用率是根据你 Kernel 消耗的寄存器和共享内存算出来的（静态指标）。而实际占用率是运行时真正在跑的活跃 Warp 比例（动态指标）。 报告指出，造成这 25.6% 落差的原因是 Warp 调度开销（Scheduling Overheads） 或 负载不均衡（Workload Imbalances）。结合下面的 Long Scoreboard 指标可以断定：大量的 Warp 因为在等显存数据（卡在 Long Scoreboard 停顿），导致硬件调度器没有足够的“处于就绪状态的 Warp”来发射指令，使得原本充裕的物理通道出现了间歇性闲置。

方案 A：引入“软件流水线”——异步或提前加载（Prefetching）

  • 原理： 不要等到马上要用数据时才去读显存，把读操作提前。
  • 做法（CUDA 11+ / Ampere 架构及以上）： 如果是从全局显存加载到共享内存，强烈建议使用 cuda::memcpy_async（异步内存拷贝）。它直接在硬件层面将数据从 Global Memory 搬运到 Shared Memory，中间不占用寄存器，这意味着线程可以一边继续做其他的计算（如上一轮循环的计算），一边让硬件在后台运下一轮的数据。

方案 B：重构内存访问模式，提高缓存命中率

  • 做法： 检查你的显存访问是否做到了合并访问（Coalesced Access）。如果访问不连续（如上一张图提示的 L2 Slices 不均衡），会导致单次读取触发多条显存事务，极大地延长了数据返回的周期，加剧 Long Scoreboard 停顿。
  • 效果： 让数据连续，让 L1/L2 缓存命中。只要数据在 L2 缓存里就被截获，返回速度会比去 DRAM 快数倍，Scoreboard 很快就能解除锁定。

方案 C：增大计算/内存比（增加 ILP：指令级并行）

  • 做法： 如果你的循环里只有一条读指令和一条计算指令，可以尝试进行循环展开（Loop Unrolling，使用 #pragma unroll），或者让一个线程一次处理 2 个或 4 个元素（比如利用 float4 读入后，连续做 4 次不相关的计算）。
  • 效果： 抛出多个不依赖的读取请求（Memory-level parallelism），并用不依赖该数据的其他计算指令去填补等待的空白期，以此来“欺骗”硬件调度器。

二、 主机锁页内存分配：cudaHostAlloc

cudaHostAlloc 是在 CPU 端（主机端） 分配内存的函数。但它分配的不是普通的内存，而是 锁页内存（Pinned Memory / Page-locked Memory）。

C++

1. 什么是“锁页内存”？为什么需要它？

普通的 C 语言 malloc 分配的是可分页内存（Pageable Memory）。操作系统为了节省物理内存，随时可能会把这块内存交换到硬盘的虚拟内存中（Page Out）。

当 GPU 想通过 PCIe 总线从普通的 Host 内存复制数据时，系统由于担心数据被操作系统移动，必须先在 CPU 内存里开辟一块隐藏的“锁页缓冲区”，把你的数据复制过去，然后再从这个缓冲区通过 PCIe 传给 GPU。这导致了两次复制，浪费了时间。

使用 cudaHostAlloc 则是直接告诉操作系统：“锁定这块物理内存，绝对不准交换到硬盘，也不准改变物理地址。”

2. 它的优势与代价

  • 优势 1（更高带宽）：GPU 可以通过 DMA（直接内存访问）直接从该内存拿数据，跳过中间缓冲，传输速度显著提升（通常能提升 30%~50% 甚至更多）。
  • 优势 2（异步传输的先决条件）：只有锁页内存，才能支持后面要讲的 cudaMemcpyAsync（异步拷贝）。
  • 代价：由于内存被死死锁住，系统可用的物理内存变少了。如果过度分配 cudaHostAlloc，会导致整个操作系统变得极度卡顿。

三、 异步内存拷贝：cudaMemcpyAsync

传统的 cudaMemcpy 是同步的（会把 CPU 死死卡住直到传输完毕）。而 cudaMemcpyAsync 是它的异步非阻塞版本。

C++

1. 核心机制

  • 参数：
    • dst / src / count / kind：目标地址、源地址、字节数、拷贝方向（如 cudaMemcpyHostToDevice），这四个与同步版本完全一致。
    • stream：流参数。指定将这个拷贝任务放进哪一个 CUDA 流队列中。
  • 特性（CPU 立即返回）： 当 CPU 执行到这一行时，它仅仅是向 GPU 的底层硬件驱动队列下发了一条“搬运数据”的指令，耗时基本为 0，随后立刻返回执行下一行代码。此时，数据的传输动作在 GPU 后台默默进行。

2. 成功触发异步的两大死理（极其重要）

新手经常发现自己写了 cudaMemcpyAsync，但程序运行速度没有任何提升。要让它真正实现异步，必须满足以下两个条件：

  1. Host 端必须使用锁页内存：如果 src 或 dst 位于主机端，它必须是由 cudaHostAlloc（或 cudaMallocHost）分配的锁页内存。如果是普通的 malloc 内存，CUDA 内部会自动将其退化为同步传输。
  2. 必须使用非默认流：传入的 stream 参数不能是默认的 0 流。因为默认流具有隐式同步的特性，会打断所有的并行。

一、 智能的“二合一”内存：cudaMallocManaged

cudaMallocManaged 分配的是 统一内存（Unified Memory，简称 UM）。它是英伟达在 CUDA 6.0 引入的极具革命性的技术。

C++

1. 核心机制（什么是统一内存？）

在过去，我们需要分别维护 Host 指针（h_ptr）和 Device 指针（d_ptr），并手动写 cudaMemcpy。 而 cudaMallocManaged 只分配一个指针（devPtr）。这个指针极其神奇：CPU 可以直接读写它，GPU 也可以直接读写它。

2. 底层黑科技：页错误（Page Fault）与自动迁移

你可能会问：两块硬件物理上是分开的，为什么能共用一个指针？ 它的底层依赖于操作系统的 页表错误（Page Faulting） 机制：

  1. 当你调用 cudaMallocManaged(&ptr, size) 时，系统并没有立刻在 CPU 或 GPU 上真正分配物理内存，只是规划了一张“虚拟地址映射表”。
  2. CPU 读写 ptr：如果数据此时在 GPU 端，CPU 访问会触发一个硬件中断（Page Fault），CUDA 驱动会自动通过 PCIe 总线把数据从 GPU 抓回内存，让 CPU 读写。
  3. GPU 读写 ptr：当你在核函数里使用 ptr 时，如果数据在 CPU 端，GPU 同样会触发 Page Fault，驱动会自动把数据迁移到显存中。

3. 优缺点分析

  • 绝对优势：
    • 代码极度简化：删掉了 90% 的 cudaMemcpy 核心代码，写 CUDA 就像写普通 C++ 一样简单。
    • 支持内存超售（Over-subscription）：在支持的架构上（如 Pascal 及之后），如果 GPU 显存只有 11GB，但你分配了 32GB 的统一内存，程序不会崩溃。CUDA 会像操作系统使用虚拟内存一样，在需要时自动在内存和显存之间换入换出。
  • 劣势：
    • 初次访问延迟高：因为数据是“按需动态迁移”的，第一次触发 Page Fault 会带来显著的延迟。
    • 控制上限较低：对于极致的高性能计算，自动迁移的效率往往不如你手动用 cudaMemcpyAsync 编织的流水线（03_3代码）。

二、 传统的 C++ 普通内存（可分页内存）

这就是我们在写普通 C++ 程序时，通过 new、malloc 或者 std::vector 分配的内存。在 CUDA 的语境下，它被称为 可分页主机内存（Pageable Host Memory）。

1. 核心机制

  • 它是完全受操作系统虚拟内存管理器控制的。操作系统为了防止物理内存爆满，随时会把这块内存的物理页交换到硬盘的 Swap 分区（虚拟内存）中，此时它的物理地址是会随时改变的。

2. 在 CUDA 中的局限性

  • 无法用于异步拷贝：如前所述，由于它的物理地址随时在变，GPU 的 DMA（直接内存访问）引擎无法直接抓取它。如果你对它使用 cudaMemcpyAsync，CUDA 内部会默默将其退化为普通的同步拷贝。
  • 传输速度慢：每次你用 cudaMemcpy 传输普通 C++ 内存的数据时，CUDA 驱动都需要在后台偷偷干两件事：
    1. 在系统内部临时申请一块临时的“锁页内存”；
    2. 把你的普通 C++ 内存数据复制到这块临时锁页内存，然后再传给 GPU。 这无形中造成了 CPU 内部的二次拷贝，极大地压低了 PCIe 的传输带宽。

二、 它们之间是如何一步步映射的？

当我们提交一段多流代码时，软件层面的 Stream 任务是如何一步步落到硬件上执行的？

步骤 1：Stream（软件） →\rightarrow→ 硬件指令队列 (HWS)

当你向 Stream0 和 Stream1 异步提交了两个不同的核函数（Kernel 0 和 Kernel 1）时，CUDA 驱动和 GPU 内部的 硬件调度器（Hardware Vector Scheduler / Host Interface） 会接管这两个流。

  • 只要这两个流是非默认流，硬件调度器就会把它们视为两个相互独立、没有依赖关系的任务源。

步骤 2：Grid →\rightarrow→ SM（软件网格映射到硬件工厂）

每一个 Kernel 在发射时，都对应一个由大量线程块组成的 Grid（网格）。

  • 硬件调度器会以 Block（线程块） 为最小单位，把 Kernel 0 和 Kernel 1 的 Blocks 动态分发给显卡上的各个 SM。

  • 🔥 核心重叠点（Stream 与 SM 的关系）：

    如果你的 GPU 上有 80 个 SM，而 Stream0 的 Kernel 0 规模很小，只占用了 20 个 SM。此时，硬件调度器发现还有 60 个 SM 闲着，它就会立刻把 Stream1 的 Kernel 1 的线程块也分发到剩下的 SM 上去运行！

    结论：在同一时刻，同一个 SM 内部可以同时并存来自不同 Stream 的不同线程块；或者说，不同的 SM 可以同时在跑不同 Stream 的任务。这就是**流并发（Concurrent Kernel Execution）**的硬件本质。

3. Block →\rightarrow→ Warp →\rightarrow→ CUDA Core（硬件微架构的执行）

当 Block 被指派到某个具体的 SM 后，SM 内部的 Warp Scheduler（线程束调度器） 会把 Block 进一步拆解为 32 个线程一组的 Warp（线程束）。

  • SM 会根据指令准备情况，调度这些 Warp 去轮流使用 SM 内部的 CUDA Core（执行单精度浮点运算 FP32、整数运算 INT32 等）。
  • Warp 是硬件上真正的基本执行单元。一个 Warp 里的 32 个线程在同一时刻必须执行同一条指令（SIMT 架构），它们会并排霸占 32 个 CUDA Core 进行计算。

三、 用一个生动的“工业园区”来做比喻

如果把整块 NVIDIA 显卡比作一个大型现代化工业园区：

  • CUDA Core 是“流水线工人”：他们什么都不懂，只会机械地做最基础的加减乘除（ALU 计算）。
  • SM 是“生产车间”：每个车间里有 128 个工人（CUDA Core），并配备了共享的原材料仓库（Shared Memory/寄存器）和车间主任（Warp Scheduler）。车间主任负责指挥哪 32 个工人上去同时干一模一样的活（Warp 执行）。
  • 整个 GPU 就是“工业园区”：里面整整齐齐排着 100 个这样的生产车间（SM）。
  • CUDA Stream 是“订单传送带”：
    • 程序员是厂长。你开了 4 条独立的传送带（4个 Stream）往园区里送原料和需求。
    • Stream0 送来的是一批“造手机（Kernel 0）”的 Block 组件；Stream1 送来的是一批“造手表（Kernel 1）”的 Block 组件。
    • 园区的总调度室（硬件调度器）一看，1车间到50车间现在空着，去造手机（Stream0）；51车间到100车间也空着，去造手表（Stream1）。
    • 甚至，如果 1 车间的空间和原材料很大，它可以前半边流水线造手机，后半边流水线造手表（同一个 SM 同时并发运行多个 Stream 的 Block）。

一、 什么是 CUDA Stream？（通俗定义）

在英伟达官方的定义中：CUDA Stream 是一系列由 CPU 主机端发射、并在 GPU 设备端按照严格顺序执行的异步操作序列。

用大白话来解释：

  • 它就是一个“先进先出”（FIFO）的硬件任务队列。
  • 你（CPU）往这个队列里扔进一连串的任务（比如：H2D拷贝、跑核函数、D2H拷贝）。
  • GPU 拿到这个队列后，会像排队买奶茶一样，严格按照你扔进去的先后顺序，一件一件地执行。执行完第一件，才会动第二件。

为什么需要它？

如果没有流，GPU 就像一个单核 CPU，只能做完一件事再做下一件。有了流，CPU 可以同时创建多个队列（Stream0, Stream1…）。GPU 内部有不同的硬件引擎（计算引擎、拷贝引擎），它们可以同时去处理不同流里的任务，从而实现并行的流水线。

二、 默认流（Default Stream） vs 非默认流

在 CUDA 中，流分为两大类：

  1. 默认流（Default Stream / NULL Stream / 0流）
    • 特点：如果你在写代码时不指定任何流参数（比如普通的 cudaMemcpy，或者核函数配置不写第四个参数 kernel<<<b, t>>>()），任务就会自动跑在默认流里。
    • 致命缺点：默认流是隐式同步的。它是一个“恶霸”，当它在 GPU 里运行时，会霸道地拦截其他所有流，导致其他流无法与它并行。
  2. 非默认流（Non-default Stream）
    • 特点：由程序员通过代码显式创建（如你代码里的 cudaStreamCreate）。
    • 优点：它们彼此之间是完全独立、互不干扰、互不阻塞的。

GPU中每个SM都能支持数百个线程并发执行，每个GPU通常有多个SM，当一个核函数的网格被启动的时候，多个block会被同时分配给可用的SM上执行。

线程束

CUDA 采用单指令多线程SIMT架构管理执行线程，不同设备有不同的线程束大小，但是到目前为止基本所有设备都是维持在32，也就是说每个SM上有多个block，一个block有多个线程（可以是几百个，但不会超过某个最大值），但是从机器的角度，在某时刻T，SM上只执行一个线程束，也就是32个线程在同时同步执行，

SIMD vs SIMT

单指令多数据的执行属于向量机，比如我们有四个数字要加上四个数字，那么我们可以用这种单指令多数据的指令来一次完成本来要做四次的运算。这种机制的问题就是过于死板，不允许每个分支有不同的操作，所有分支必须同时执行相同的指令，必须执行没有例外。
相比之下单指令多线程SIMT就更加灵活了，虽然两者都是将相同指令广播给多个执行单元，但是SIMT的某些线程可以选择不执行，也就是说同一时刻所有线程被分配给相同的指令，SIMD规定所有人必须执行，而SIMT则规定有些人可以根据需要不执行，这样SIMT就保证了线程级别的并行，而SIMD更像是指令级别的并行。

Day 11：Warp与线程束分化（Warp Divergence）

Warp内的线程会锁步执行——即所有线程同时执行同一条指令，但有些线程可以“被屏蔽”（不激活），这就是SIMT（单指令多线程）模型

什么是线程束分化？

当一个warp内的线程因为条件分支（如if-else）而需要执行不同的指令序列时，GPU必须依次执行这些分支：先执行if路径，屏蔽掉else线程；再执行else路径，屏蔽掉if线程。

性能影响：最坏情况下，warp内32个线程各自取不同分支，GPU需要串行执行32次，性能降低32倍。

  • 均匀划分：让同一warp内的线程尽量走同一分支
  • 利用线程束内的一致性：如果可以，在分配数据时按warp维度对齐

Day 14：阶段项目——矩阵乘法优化

目标：完成从CPU版本到共享内存优化版本的完整优化过程。

背景知识：矩阵乘法C = A × B，其中A是M×K，B是K×N，C是M×N。

每个输出元素C[i][j]需要计算K次乘加：C[i][j] = sum_{k=0..K-1} A[i][k] × B[k][j]。

朴素GPU方案的瓶颈：每个线程计算一个输出元素，需要从全局内存中读取A和B。由于重复读取同一个A/B元素，导致全局内存带宽浪费。

优化方案（Tiling + 共享内存） ：

  1. 将A和B划分成小块（Tile），每个Block加载一个Tile到共享内存
  2. 在一个Block内，线程协作计算多个输出元素
  3. 每次从共享内存中读取数据，避免重复的全局内存访问

朴素gpu4原理是什么?

像是在 GPU 显存上布置了百万级的“吸血管道”：

  1. 空间并行：GPU 瞬间铺开 M×NM \times NM×N 个硬件线程，每个线程死死盯住结果矩阵 CCC 的一个物理格子。
  2. 独立内积：每个线程各自拉取自己需要的那一整行 AAA 和那一整列 BBB，在自己的寄存器里做高频的乘加。
  3. 就地收尾：计算完毕后，百万线程同时往全局内存 CCC 写入一笔数据，整个矩阵乘法瞬间宣告结束。

Day 16：异步执行模型与流的基础概念

第一部分：核心概念（上午，1.5小时）

目标：理解“异步”在CUDA中意味着什么，以及流为什么是并发的核心工具。

核心精要理解：

到目前为止，你写的每个CUDA程序都遵循这个模式：分配内存 → 拷贝数据到GPU → 启动kernel → 拷贝结果回CPU → 释放内存。每一步都是同步的——cudaMemcpy会阻塞CPU直到传输完成，kernel启动虽然立即返回，但你总会在后面加一个cudaDeviceSynchronize()来等待。

现代 GPU 内部通常拥有独立的硬件引擎：

  1. Copy Engine (CE) - 拷贝引擎：专门负责 PCIe 总线的数据传输（有 H2D 和 D2H 两个双工通道）。
  2. Execution Engine (EE) - 计算引擎：专门负责执行 CUDA 核函数（SM 核心）。

但CUDA的真正威力在于异步并发执行：

  1. CPU和GPU可以同时工作：kernel启动后立即返回，CPU可以继续做其他事（如准备下一批数据），GPU同时在计算
  2. GPU内部的拷贝引擎和计算引擎可以同时工作：数据从CPU传输到GPU的同时，GPU可以在计算另一批数据
  3. 多个kernel可以同时运行：如果GPU有足够的资源，不同流中的kernel可以并行执行

流的本质：

CUDA流是一个命令队列——你把内存拷贝、kernel启动等操作按顺序放进流里，GPU按顺序执行这个流中的命令。

  • 默认流（NULL流） ：所有操作都在这个流中顺序执行，且具有隐式同步行为——默认流中的操作会阻塞其他流
  • 非默认流：不同流中的操作可以并发执行（是否真的并发取决于硬件能力和资源）

关键原则：流提供了并发可能性，但不保证并发一定发生。是否真的并发取决于GPU是否有空闲的拷贝引擎和计算引擎

1. D2H（拷回）阻碍了后续的 H2D（流水线阻塞）

在单拷贝引擎上，你目前在一个流里的顺序是：H2D -> Kernel -> D2H。 当 chunk 0 运行到 D2H 时，它会霸占拷贝引擎，导致 chunk 2 的 H2D 必须等待。

  • 更高级的玩法（多流分配）： 如果拆成 4个流（2个专门负责 H2D，2个专门负责 D2H），并使用信号量（Event）进行跨流同步，可以让拷贝引擎上的任务排列得更紧密，榨干最后一丝带宽。

2. 块大小（CHUNK_N）的黄金隐性约束

你现在设置的 CHUNK_N 是 1M float（4MB）。

  • 如果 CHUNK 太大：比如分块变成 64MB，总共只有 2 块，那么流水线的“热身（Warm-up）”和“收尾（Cool-down）”时间占比太大，重叠效果不明显。
  • 如果 CHUNK 太小：比如每块只有 1KB。虽然分块多了，但由于每次触发 PCIe 传输都有固定的硬件延迟（Overhead），过小的传输会导致带宽跑不满（无法达到 PCIe 饱和带宽）。

💡 小实验：你可以尝试修改 CHUNK_N 分别为 256KB, 4MB, 16MB，观察总耗时（total_ms）的变化曲线，找出你这台笔记本上的 Sweet Spot（最佳平衡点）。

核心精要理解：

刺客 1：广度优先（Breadth-First）vs 深度优先（Depth-First）提交

这是多流编程中最经典的代码设计陷阱。

  • ❌ 错误的提交方式（广度优先）：

    • 后果：因为硬件队列是按 CPU 提交顺序排队的。这会导致 3 个 H2D 把拷贝引擎塞满，然后 3 个 Kernel 把计算引擎塞满。完全无法产生交错重叠！

    • 效果：这样提交，底层硬件才能看到 Kernel_0 和 H2D_1 同时就绪的机会，从而触发重叠。

刺客 2：显卡驱动的“单硬件队列”限制（Hyper-Q 技术）

  • 在老旧的 GPU（Kepler 架构之前）上，虽然你开了多流，但驱动层只有一个硬件网格队列（Hardware Work Queue）。不同流的命令混在一起，依然会退化成串行。
  • 现代硬件（你的 Ampere 架构）：支持 Hyper-Q 技术（拥有多达 32 个独立的硬件工作队列）。你的 stream0 和 stream1 会被分发到不同的硬件管道中，这才保证了真正的 流间互不干扰。

刺客 3：数据块大小（Chunk Size）的物理极限

  • 太小（如 1KB）：每一次 cudaMemcpyAsync 触发 DMA 传输，操作系统和 PCIe 总线都有大约几微秒的 固有的启动开销（Overhead）。如果分块太小，总线带宽还没跑满就传输结束了，时间全浪费在握手切换上。
  • 太大（如 128MB）：如果总共就切了 2 块，那么只有在两块交接的中间那一点点时间有重叠，首尾的大部分时间 GPU 还是在单兵作战（热身和收尾时间太长）。

Day 21：CUDA Graph入门

第一部分：核心概念（上午，1.5小时）

目标：理解CUDA Graph是什么、解决什么问题、如何基本使用。

核心精要理解：

到目前为止，你每次启动kernel都要经过CPU→GPU的调度路径。对于少量大kernel，这个开销微不足道。但当你在循环中反复启动大量小kernel时，CPU的启动开销可能成为瓶颈。

CUDA Graph的核心思想：

  1. 录制（Capture） ：先执行一次完整的操作序列，CUDA运行时“记住”了所有操作 cudaStreamBeginCapture, cudaStreamEndCapture
  2. 回放（Launch） ：后续直接以极低开销重放整个图，跳过CPU调度cudaGraphInstantiate cudaGraphLaunch

类比：普通执行就像每次做菜都看菜谱一步步来；CUDA Graph就像把菜谱背下来，以后每次直接做。

适用场景：

  • 循环中反复执行相同的kernel序列（如深度学习训练迭代）
  • 多个小kernel频繁启动
  • 需要最低延迟的场景

核心痛点：为什么需要 CUDA Graph？

在传统的流（Stream）模式下，每次你调用 kernel<<<...>>>，CPU 都会发生以下事情：

  1. 参数打包：将内核参数放入驱动层缓冲区。
  2. 驱动层校验：检查硬件资源、流状态。
  3. 硬件入队：将任务推送到 GPU 的命令队列。
  • 传统 Stream（流）：属于命令式（Imperative）执行。每次循环，CPU 都要重新走一遍上述流程。如果 Kernel 运行时间只有 5 微秒，而 CPU 调度开销却要 10 微秒，GPU 就会经常处于“饿死”状态。
  • CUDA Graph：属于声明式（Declarative）执行。它把整个执行流固化成一个拓扑图（DAG），CPU 一次性提交给 GPU，GPU 自己按照图的依赖关系执行，彻底解放了 CPU。

1. 归约算法 (Reduction)

核心思想：树状折半归约

不能让一个线程去加所有数，而是让所有线程两两对半分担。

  • 后续轮次：不断折半，直到最后只剩一个值。

3. 排序算法 (Sorting)

方案 A：双调排序 (Bitonic Sort) —— 适合小规模/固定长度

  • 原理：它是一种排序网络（Sorting Network）。它的比较顺序是完全固定的，与输入的数据内容无关。
  • 特点：完美契合 GPU。因为比较路径固定，没有任何条件分支发散！
  • 核心操作：不断将序列变成“先升后降”的双调序列，然后再将双调序列拆分合并。

方案 B：基数排序 (Radix Sort) —— 工业界主力 (如 Thrust 库)

对于大规模数据，基数排序是 GPU 上的绝对王者，时间复杂度为 O(N)O(N)O(N)。

  • 核心步骤：
    1. 每次只看数据的一个位（比如二进制的最后 4 位，即基数为 16）。
    2. 直方图统计（Histogram）：统计当前位上，0~15 每个桶里有多少个元素。
    3. 前缀和（Scan）：对直方图结果做全局 Scan，计算出每个桶在输出数组中的起始偏移地址。
    4. 数据重排（Scatter）：每个线程根据自己数据的位值和 Scan 出来的地址，把数据写到正确的位置。
    5. 移向高位，重复上述步骤。

任何一个没有达到性能极限的 Kernel，其瓶颈必然归属于以下三大受限之一：

1. 内存受限 (Memory Bound)

  • 表现：DRAM 或各级缓存（L1/L2）的带宽利用率（如 dram__bytes.sum.per_second）接近硬件理论极限，但计算单元大部分时间在“等米下锅”。
  • 典型病因：访存未对齐、不连续（非合并访存）、没有有效利用 Shared Memory 导致频繁读取全局内存（Global Memory）。

2. 计算受限 (Compute Bound)

  • 表现：流水线吞吐率非常高，某类计算指令（如浮点加乘、Tensor Core 指令）的计数器爆表，而内存带宽还有很大富余。
  • 典型病因：这通常是个好信号，说明你充分利用了硬件。如果还想优化，需要考虑算法层面的剪枝、将特殊数学函数替换为硬件级低精度指令（如使用 __fadd_rn 等内联函数），或使用 Tensor Core 代替普通 ALU。

3. 调度/延迟受限 (Latency Bound)

  • 表现：计算和内存的利用率都很低，执行总时间 gpu__time_duration.sum 却很长。
  • 典型病因：指令流水线存在长延迟（Long Scoreboard Stall）。最常见的是活跃 Warp 数（Occupancy）太低，导致当某个 Warp 因为读取内存而挂起时，SM 找不到其他可以顶替上来的 Warp，使得计算单元集体“发呆”。

💡 核心痛点：为什么不直接编译成机器码，而要多一个 PTX？

  • 硬件迭代太快：从 Kepler、Pascal、Volta、Ampere 到 Blackwell，NVIDIA GPU 的底层硬件架构（如寄存器文件数量、指令流水线、Tensor Core 内部设计）在剧烈变动。
  • 解耦与兼容性（JIT 编译）：PTX 是一种虚拟指令集。你在 5 年前编译的 CUDA 程序中包含的 PTX 代码，在今天最新的 GPU 上运行时，驱动程序（JIT 编译器）会自动将这段 PTX 翻译成针对当前最新显卡优化的 SASS。这保证了 CUDA 生态的向前兼容性。

核心概念二：PTX 的语法骨架与“三大基石”

PTX 的可读性其实比传统的 8086 或 ARM 汇编要好得多，因为它保留了高级语言的数据类型和无限寄存器的伪抽象。阅读 PTX 时，抓准以下三个核心：

1. 强类型指令后缀

PTX 指令必须通过.类型明确指定操作数的数据宽度和性质。

  • 整数：.u32 (无符号32位), .s64 (有符号64位)
  • 浮点数：.f32 (单精度), .f64 (双精度)
  • 谓词/布尔：.pred (用于条件跳转或分支)

你在 CUDA C++ 中常用的内置变量（如 threadIdx.x），在 PTX 中对应着特殊的只读寄存器：

  • %tid.x, %tid.y →\rightarrow→ threadIdx.x, threadIdx.y

有两个主要原因导致了 %r0 的缺席：

原因 A：PTX 的区间声明语法（主要原因）

原因 B：编译器的后端优化与死代码消除（Dead Code Elimination）

在编译的最早期阶段，编译器可能确实用过 %r0（例如用来存某个中间变量）。但当高级优化器（Optimizer）介入后，发现这个中间变量可以和其他指令合并（比如合并成了 mad 指令），或者发现某行代码是死代码并将其删除了。

虽然代码被删了，但前端的寄存器声明数量（.reg .b32 %r<6>）为了省事或保持对齐，通常不会再回过头去精确地把它改成不连续的形式。

🛠️ 你不用担心浪费：SASS 会重新洗牌

不用担心 %r0 的缺席会浪费显卡宝贵的硬件寄存器。

Day 37：多GPU编程与NCCL基础

第一部分：核心概念（上午，1.5小时）

目标：了解多GPU编程的基本模型，掌握NCCL通信库的基础使用。

核心精要理解：

为什么需要多GPU？

单个GPU的显存和计算能力有限。当模型或数据集超出单卡容量时，或者需要更快的训练/推理速度时，就需要多GPU并行。

多GPU编程的两种模式：

模式 说明 适用场景
数据并行 每张卡持有完整模型，处理不同数据 数据量大，模型适中
模型并行 每张卡持有模型的一部分 模型超大（如GPT）

NCCL（NVIDIA Collective Communications Library）

NCCL是NVIDIA开发的多GPU通信库，提供高效的集合通信操作：

操作 说明
AllReduce 所有GPU的数据求和/求平均后广播给所有GPU
Broadcast 从一个GPU广播数据到所有GPU
AllGather 收集所有GPU的数据并广播
ReduceScatter 归约后分散到各GPU

核心概念一：数据并行 vs 模型并行（大白话拆解）

多卡编程的核心任务，就是把一个原本单卡放不下的“超级大任务”，拆分到多张显卡上。拆分的方法主要有两种：

1. 数据并行 (Data Parallelism, DP)

  • 大白话：“每人一本相同的书，各自做不同的作业”。
  • 怎么做：每张 GPU 的显存里都塞入一个一模一样的模型。把海量的数据（Batch）切分成好几份，GPU 0 算第一份，GPU 1 算第二份…… 它们各自算完之后，把结果（梯度）汇总对齐一下，再更新模型。
  • 痛点：如果模型本身超大（比如 70B 的大模型，单卡显存连模型权重都装不下），这种方法就彻底瘫痪了。

2. 模型并行 (Model Parallelism, MP)

  • 大白话：“流水线工厂，一人负责组装一部分”。
  • 怎么做：模型太大了，一张卡放不下，那就“切两半”。GPU 0 负责前 50 层的计算，GPU 1 负责后 50 层的计算。GPU 0 算完的中间结果（Activation），通过高速通道传给 GPU 1 继续算。
  • 痛点：显卡之间会产生高频、大量的中间数据传输。如果传输太慢，GPU 1 就会经常处于“等米下锅”的闲置状态。

核心概念二：NCCL 集合通信的四大神兵利器

当多张显卡在一起协同工作时，它们之间必须频繁地交换数据。如果让你用传统的 cudaMemcpyPeer（点对点拷贝）手写多卡数据同步，代码会变成一团乱麻，且性能极差。

NVIDIA 官方推出的 NCCL（读作 Nickel） 专门用来解决多卡、多机之间的集合通信（Collective Communications）问题。你必须熟练掌握以下四个核心操作：

1. Broadcast（广播）

  • 动作：由一个特定的“源 GPU”（通常是 Root，如 GPU 0）把手里的一份数据，原封不动地复制发送给集群中的所有其他 GPU。
  • 场景：初始化时，Rank 0 产生了一组随机权重，广播给所有卡，确保大家起点一致。

2. AllGather（全收集）

  • 动作：每个 GPU 手里都有一份不同的小数据（大小为 NNN）。执行完后，所有 GPU 的显存里都同时拥有了所有人拼接在一起的总数据（大小为 K×NK \times NK×N）。
  • 场景：序列并行或分布式特征提取，把各卡算出的局部 embedding 拼回完整的全局特征。

3. ReduceScatter（归约分散）

  • 动作：每个 GPU 手里有一份相同大小的数据。首先把所有卡对应位置的数据进行数学运算（如求和），然后把这个求和后的总数据切成 KKK 份，每张卡分到其中的一份。
  • 场景：ZeRO（零冗余优化器）技术的核心，用来切分和分散存储梯度与优化器状态。

4. AllReduce（全归约——最核心、最常用）

  • 动作：等价于先做一次 Reduce（所有卡数据求和），再做一次 Broadcast（把求和结果分发给所有人）。最终结果是：所有 GPU 在相同的位置，都得到了所有卡数据求和/求平均后的最新大表。
  • 场景：数据并行训练的灵魂。每张卡各自算出了不同的梯度，通过 AllReduce 一键实现全网梯度同步，然后大家一起整齐划一地更新模型。

Day 41：cuDNN Graph API与算子融合

第一部分：核心概念（上午，1小时）

目标：掌握cuDNN Graph API，理解算子融合的价值和实现方式。

核心精要理解：

什么是算子融合？

在深度学习中，一个简单的卷积层通常包含多个操作：卷积 → 偏置加法 → 批归一化 → 激活函数。如果每个操作都单独调用，每次都需要读写全局内存，产生大量中间结果。

算子融合将这些操作合并为一个kernel，数据在寄存器/共享内存中传递，避免中间结果的显存读写。

cuDNN Graph API：

cuDNN 8.0引入了Graph API，提供了一种声明式编程模型，将计算描述为操作图。你可以定义一个包含多个操作的有向无环图（DAG），cuDNN会将其融合并生成高效的GPU代码。

Graph API vs 传统API：

对比维度 传统API Graph API
编程模型 命令式（逐步调用） 声明式（描述图）
算子融合 手动或依赖运行时 自动融合
灵活性 较低 高
性能 好 更好（融合减少显存访问）

核心概念一：为什么要“融合”？（从访存受限看世界）

在第 34 天学习 Nsight Compute 时，我们强调过一个黄金定律：深度学习中的绝大多数非卷积算子（如 ReLU 激活、Bias 加法、Element-wise 加法）都是内存受限（Memory Bound）的。

🚨 传统非融合模式（Memory-to-Memory）

假设我们有一个最经典的深度学习管线：卷积 (Conv) ──> 偏置加 (Bias) ──> 激活 (ReLU)。

传统的单算子调用方式，其底层的显存读写轨迹是这样的：

  1. 执行 Conv：从显存读取输入，计算，将巨大的中间结果 YconvY_{conv}Yconv​ 写入显存。
  2. 执行 Bias：从显存读取 YconvY_{conv}Yconv​，加上偏置，将中间结果 YbiasY_{bias}Ybias​ 写入显存。
  3. 执行 ReLU：从显存读取 YbiasY_{bias}Ybias​，执行激活，最后将最终结果 YreluY_{relu}Yrelu​ 写入显存。

❌ 痛点：GPU 的计算单元（ALU/Tensor Core）快如闪电，但大部分时间都在痛苦地等待中间结果在“全局内存（显存）”和“芯片内部”之间搬运。这种频繁的 Read-Write 带来了极大的显存带宽浪费。

⚡ 算子融合模式（Register-to-Register）

算子融合的核心思想是：让数据在芯片内部的“寄存器（Register）”或“共享内存（Shared Memory）”中跑完所有流程，只在开始和结束时读写一次显存。

  1. 硬件将输入数据拉入芯片。
  2. 在寄存器中算完 Conv，结果不回传显存，直接在寄存器里交给 Bias 逻辑。
  3. 算完 Bias，继续在寄存器里交给 ReLU 逻辑。
  4. 最终将执行完 ReLU 的完美结果，一次性写回显存。

💡 效果：中间结果 YconvY_{conv}Yconv​ 和 YbiasY_{bias}Ybias​ 在物理显存中彻底消失了。这不仅省下了海量的显存空间，更通过消除访存延迟，让整体吞吐量飙升。

在以前，想要做到上面这种融合，工程师必须自己用手写 CUDA 内核。但面对千变万化的神经网络组合（有的加 ReLU，有的加 GeLU，有的带残差连接），手写融合内核简直是地狱难度。

cuDNN 8.x 推出的 Graph API 彻底改变了这一切。它采用的是声明式编程（Declarative Programming）：

🗣️ 命令式（传统 API）：“cuDNN，你先帮我算个卷积；算完了，你再帮我算个偏置……”

🧠 声明式（Graph API）：“cuDNN，这是我的终极目标：我要输入 XXX，经过一个包含 Conv、Bias、ReLU 的有向无环图（DAG），最后输出 YYY。图在这里，至于怎么融合、怎么最快，你自己在底层全自动生成内核吧！”

2026年6月9日 训练后量化

最近在搞量化相关的, 之前学习到的量化也只是皮毛. 什么是量化? 怎么量化?

这篇用于深入理解和使用量化, 并进行结果分析

1 前言

1.1 量化

量化分为训练后量化(PTQ)和训练时量化(QAT)

PTQ 主要是针对模型压缩后,比如int8, 带来的精度损失进行微调. 具体流程是找出最合适的 Scale（缩放因子），把 FP32 的浮点数安全地映射到 INT8 的整数范围（−128-128−128 到 127127127）。用极少量的校准数据, 提高统计学方法挽回精度的损失.

QAT 主要是对量化后得模型进行微调,找出最合适的 Scale（缩放因子）, 相当于预训练模型微调训练

量化的本质就是寻找最优映射（Scale）并尽可能减少信息损失：

  • PTQ： 考前不复习，直接用统计学公式盲猜一个最优鞋码（Scale），几分钟搞定。
  • QAT： 穿上鞋去操场上拉练几个大项（跑梯度下降训练），让鞋码（Scale）和脚（Weights）磨合到最完美的契合度。

但 QAT 比 PTQ 还多做了一件事：对抗“舍入误差”（Rounding Error）。

把浮点数变成整数，不可避免地要进行四舍五入。

  • PTQ 极其死板： 0.4 必须变 0，0.6 必须变 1。
  • QAT 极其聪明： 通过神经网络训练，模型可能会发现，在当前这一层，把 0.4 强制变成 1 反而能让后面的矩阵乘法结果更接近原版。这种“不讲理”的微调能力，是纯统计学的 PTQ 绝对做不到的。

2 PQT

2.1 具体流程

普通 PTQ 的目标是找出最合适的 Scale（缩放因子），把 FP32 的浮点数安全地映射到 INT8 的整数范围（−128-128−128 到 127127127）。它的具体步骤如下：

1. 权重（Weights）直接量化

模型的权重（比如卷积层、全连接层的参数）是固定的、静态的。

  • 工具（如 TensorRT 或 ModelOpt）会直接扫描每一层权重的最大值（Max）和最小值（Min）。
  • 映射公式非常直接：把这个最大绝对值直接映射到 INT8 的 127127127。
  • 耗时： 几秒钟，纯粹的矩阵运算。

2. 激活值（Activations）校准（Calibration）

这是普通 PTQ 最关键的一步。网络的输入和中间层的输出（激活值）是动态的，输入不同的图片或文本，中间层的数值范围大不相同。

  • 准备校准集： 抽取极少量的真实数据（通常 32 ~ 128 个样本，不需要标签）。
  • 前向跑数据（Forward Pass）： 让这些数据在 FP32 模型里跑一次，工具会像“监控摄像头”一样，记录下每一层激活值数据的分布直方图。
  • 计算激活值 Scale： 因为激活值可能存在极端的离群点（Outliers），如果直接按最大值截断，会导致大部分正常数据的精度严重压缩。所以工具会使用一些高级统计学算法来找到最佳截断点Scale：
    • KL 散度（KLD / Entropy）： 寻找一个截断点，使得量化前后的信息熵（数据分布）损失最小（TensorRT 默认视觉模型算法）。
    • Percentile（分位数）： 比如丢弃全网络最大的 0.01%0.01\%0.01% 的数据，只用 99.99%99.99\%99.99% 的最大值作为截断范围。
    • MinMax： 简单粗暴，直接用统计到的绝对最大值。

3. 合并与导出

把计算好的“权重 INT8 矩阵”和“每一层激活值的 Scale 缩放表”打包。

交给 TensorRT 后，推理时数据一进来，就乘以对应的 Scale 变成 INT8 进行硬件加速，出结果时再除以 Scale 变回浮点数。

3 QAT

3.1 具体流程

1. 自动插入“伪量化”节点（Fake-Quantization）

你不需要手动去改写 PyTorch 的网络层。ModelOpt 可以自动扫描你的 PyTorch 模型，在卷积层、全连接层、激活函数等地方自动插入 FakeQuantize 节点。

  • 原理： 在前向传播时，数据会被转换为低精度再转回高精度（模拟 INT8 的精度损失）；在反向传播时，正常的更新梯度。

2. 校准与范围学习（Calibration & Learnable Scales）

量化最难的是确定“截断范围”（Scale）。ModelOpt 提供了多种算法：

  • 它可以在 QAT 开始前，通过少量数据进行校准（Calibration），初始化一个比较好的量化范围。
  • 在 QAT 训练过程中，这个量化范围（Scale）会变成可学习的参数，随着网络权重一起优化，找到最完美的截断点。

3.2 伪量化节点

是:

在 QAT（量化感知训练）期间，普通的 PyTorch 算子（比如卷积层）其实依然在用 FP32（32位浮点数）进行计算。

在前向传播和反向传播中分别扮演不同的角色：

  • 前向传播（Forward）—— 制造伤害（模拟误差）： 当一个完美的 FP32 浮点数（比如 0.342178）流经伪量化节点时，它会执行以下操作：

    1. 量化（Quantize）：根据当前的缩放因子（Scale），把它四舍五入变成 INT8 整数（比如 87）。
    2. 反量化（Dequantize）：立刻把这个 87 再乘回 Scale，变回 FP32 浮点数（比如 0.339843）。

    这个过程故意丢失了尾部的精度（0.342178 变成了 0.339843），这就叫量化噪声。后面的卷积层吃到的就是这个“带有噪声、被污染过”的输入。

  • 反向传播（Backward）—— 绕过惩罚（传递梯度）： 当梯度传回来时，因为四舍五入函数（Round）的导数是 0，伪量化节点会使用一种叫 STE（Straight-Through Estimator，直通估计器） 的技术，直接假装什么都没发生，把后面的梯度原封不动地传过自己，让前面的层能够正常更新权重。

💡 总结它的目的：让模型在训练时，提前体验并适应未来部署到 INT8 硬件上时才会遇到的精度损失，从而在训练中自己调整权重来弥补这个损失。

二、 核心差异深层分析

1. 推理速度（Inference）的断层式碾压（5.5ms vs 1.6ms）

这是本次对比的核心亮点。为什么 TensorRT 能够把推理时间压到不可思议的 1.6ms？

  • 动态范围量化（INT8）：PyTorch 默认使用 FP32（32位浮点数）或 FP16 进行计算。而你的 TRT 引擎使用了 INT8（8位整数）。在显存体积和计算吞吐上，INT8 具有压倒性优势，RTX 3060 的 Tensor Cores 处理 INT8 矩阵乘法的速度远快于浮点数。
  • 计算图融合（Graph Fusion）：PyTorch 在运行时是逐层调用 CUDA 核函数的。TensorRT 在编译阶段（你之前等的 155 秒）将 YOLO 里的 Conv + BatchNorm + ReLU 融合成了一个单一的算子，极大减少了显存与 GPU 寄存器之间的数据拷贝（Memory Bound 优化）。
  • 核心选择（Kernel Selection）：TensorRT 针对你这块 RTX 3060 Laptop 显卡的硬件架构（Ampere 架构），在底层精选了最契合的底层 CUDA 算子。

2. 后处理（Postprocess）为什么变快了？（1.65ms vs 1.25ms）

  • 思考：后处理（如 NMS 非极大值抑制、Mask 原型系数相乘等）通常是在 CPU 或通过普通的 PyTorch 算子在 GPU 上跑的，为什么 TRT 也会变快？
  • 原因：在第二阶段导出 ONNX 过程中，YOLO 的一部分后处理节点（甚至包括部分 Gather/Slice 边界处理）被转换成了高效的 ONNX/TRT 原生算子，或者通过 TensorRT 的编译进行了优化。数据从“模型结束”到“后处理开始”的交接更加紧凑，减少了 CPU/GPU 的同步等待时间。

3. 数据一致性（业务安全）

最让人欣慰的是数据的完全一致。例如：

  • 图片 01：3 apples, 2 carrots, 1 eggplant, 4 pear_greens
  • 图片 02：2 apples, 1 carrot, 1 eggplant, 4 pear_greens

在两套引擎下数量和类别完全恒定。这证明在当前的水果实例分割场景下，TensorRT INT8 量化完全没有引发精度崩塌，你可以非常安全地在生产环境替换掉 .pt 模型。
