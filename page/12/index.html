代码模型

模型加密

模型加密的几个方式：

  • 模型文件直接加密，把模型的二进制文件直接加密，一般都会有加密算法，对模型的前xx字节进行加密，解密的时候对前xx字节进行解密即可，这种加密只在load时候做，会影响模型加载速度，但是不影响运行速度
  • 模型结构不加密，模型权重加密，有的可以采用类似于模型压缩的方法把权重压缩了，推理时以自定义协议读取加载推理
  • 也需要对解密模型的代码进行加密，代码混淆要做，不过这样会影响解密代码也就是load模型过程，会变慢，就看你代码混淆做到什么程度

模型转换

模型可能是各种格式的：

  • Caffe
  • ONNX
  • Pytorch
  • TFLITE
  • NCNN、MNN

模型转换后一般要做

  • 转换后看一下模型的输入输出类型、维度、名称、数量啥的是否和之前一致
  • 转换后首先跑一张训练时的图（或者一批图），看下新模型的输出和旧模型差多少，一定要保证最终输入到模型的tensor一致（也可以使用random输入或者ones输入测试，不过对于模型权重分布特殊的模型来说，对于这种输入可能评测不是很准确）
  • 批量跑测试集测一下精度是否一致
  • benchmark转换后模型的速度是否符合预期

常见的问题

  • 转换后模型精度问题，输出为nan、精度完全错乱
  • 转换后模型batch=1正常，多batch结果错乱
  • 转换后输入/输出类型维度啥的错误
  • 转换后模型速度未达到预期
  • 未完待续

模型优化

小到优化一个op（Op就是Kernel的集合，一个Op代表的是有一定共性的多个Kernel便于在计算图和图优化中进行表示），大概优化整个推理pipeline，可以干的事情很多。

合并、替换op算子

很多框架在导出的时候就会自动合并一些操作，比如torch.onnx在导出conv+bn的时候会将bn吸到前面的conv中，比较常见了。
但也有一些可以合并的操作，假如框架代码还没有实现该pattern则不会合并，不过我们也可以自己合并，这里需要经验了，需要我们熟知各种op的合并方式。
可以自己合并一些操作，比如下图中的convTranspose+Add+BN，是不常见的Squence(序列)的pattern，如果自己愿意的话，可以直接在ONNX中进行合并，把权重关系搞对就行

列举一些合并的例子，总之就是将多个op合成大op，节省计算量以及数据搬运的时间：

  • conv/transposeConv+bn

量化

量化目前比较成熟，也有很好的教程（PPQ），很成熟的库（PPQ）

  • 量化基本概念，与硬件的关系
  • PTQ量化和QAT量化，两种量化还有很多方法。PTQ有 EasyQuant（EQ）、；QAT有LSQ(Learned Step Size Quantization)、DSQ(Differentiable Soft Quantization)

不是所有模型、所有op都适合量化：

  • 重参数量化 https://tech.meituan.com/2022/09/22/yolov6-quantization-in-meituan.html
  • 量化模型直接输入int8 进行测试

注意点：

  • 有些模型量化后，虽然整体指标没有变化（某个评价标准，比如coco的mAP），但是实际使用中，发现之前的一些效果变差了，这种情况大多是调用模型的策略效果与这个模型的耦合度比较高了。举个例子，比如之前这个模型对小目标检测效果好，但是量化后，小目标检测效果差了（然而中目标效果好了）所以导致与小目标耦合度比较高的策略兼容度不高，导致算法的整体精度下降。这种情况就比较尴尬，你可以调整策略，或者重新量化模型，加上一些约束使其在某些场景下尽可能和原始模型表现一致，但这个需要时间去优化了，有较高的时间成本。

0 源码包与二进制包什么区别？

Python 包的分发可以分为两种：

1、以源码包的方式发布

源码包安装的过程，是先解压，再编译，最后才安装，所以它是跨平台的，由于每次安装都要进行编译，相对二进包安装方式来说安装速度较慢。

2、以二进制包形式发布

二进制包的安装过程省去了编译的过程，直接进行解压安装，所以安装速度较源码包来说更快。

由于不同平台的编译出来的包无法通用，所以在发布时，需事先编译好多个平台的包。

局部变量还是变成 self.

什么时候该变成 self.（满足其一再考虑）

  • 跨方法复用：后续有别的方法（不是当前函数）也需要用到同一份值，并且调用链不方便通过参数传递。
  • 生命周期跨帧/跨次调用：你希望“下一帧”还读到“上一帧”的 center_nearest_depth（例如做平滑、滤波、跟踪、回退策略）。
  • 显式缓存：计算很贵，且在同一对象生命周期内可复用（并且有清晰的失效条件）。

不建议变成 self. 的主要原因（这段代码更像“每次都重新算”）

  • 避免陈旧状态：某一帧没算出来/走了 else 设成 0.0，如果写到 self，很容易被别处误用成“真实深度”或被下一次处理误读。
  • 并发/复入风险：如果同一个 Processor 实例被多线程或异步复用（常见于视频流管线），self.xxx 会引入竞态；局部变量天然线程安全。
  • 语义更清晰：局部变量 = 本次计算产物；self = 对象长期状态/配置/缓存。读代码的人更不容易误解。

模块级全局变量

为什么 base.py 里 _pools / _db_ensured 是“全局变量”？算不算“真的全局”？

是的，它们是 模块级全局变量（module-level globals）：

  • 为什么是全局：它们定义在 app/core/database/base.py 的最外层作用域，不在任何函数/类里面：
  • “全局”的范围：它们对 同一个 Python 进程 来说是全局且单例的（import app.core.database.base 的所有地方都会共享同一份 _pools / _db_ensured）。
    • 但它们不是跨进程全局：如果你开了多个 worker/进程（例如 gunicorn/uvicorn 多进程），每个进程都会有自己的一份 _pools。
  • 为什么要这么设计：为了实现 get_pool(db_name) 的缓存复用——同进程同库名只创建一次连接池，避免每个业务模块各自 create_pool() 把连接数叠加。

真正会“消失/销毁”的典型场景只有：

  • 进程退出/重启：内存整体释放。
  • 你主动 close_pool/close_all_pools 并从 dict 里 del 掉：引用断开，才可能被回收。
  • 热重载/重复启动：旧进程退出，新进程重新 import，新的一份全局变量重新创建。

垃圾回收

Python 垃圾回收机制（和这里的关系）

Python（CPython）主要是两套机制一起工作：

  • 引用计数（立即释放为主）

    • 每个对象都有引用计数 refcount。
    • 当 refcount == 0 时，对象会立刻被释放（调用 __del__/资源释放逻辑如果有）。
    • 你这里：_pools[db_name] = pool 让 pool 的引用计数至少为 1，所以不会到 0，不会释放。

  • 循环垃圾回收（处理“互相引用但外部不可达”的对象）

    • 解决：A 引用 B、B 引用 A，导致引用计数都不为 0，但外部已经访问不到。
    • GC 会定期扫描，发现“不可达的循环引用”就回收。
    • 你这里：不是循环引用问题，而是仍然可达（从模块全局 dict 可达），所以 GC 也不会动。

把池放在模块全局，本质上是“进程级单例资源”，应当在应用 shutdown 时显式关闭。

懒加载

1. 懒加载对内存的优势

前提：资源“够大 + 不一定会用到”时，懒加载才有意义。

  • 减少“永远没用上的占用”
    某些大对象（长 prompt、大配置 dict、大模型权重）如果只在少数请求场景下用到，懒加载可以让：
    • 没触发那个场景的进程，完全不为它分配内存。
  • 降低启动时内存峰值 & 加快启动
    • 进程启动只加载必要东西，其他按需创建，可以让服务：
      • 启动更快
      • 刚启动时的内存占用更小
  • 易于“加载后再释放”
    • 有的懒加载实现会加“过期/清理”策略，用完一段时间又释放，进一步控制长期占用。

如果只是几 KB 的字符串模板，收益很有限；如果是几十 MB 的大表/大模型，就很值。

  2. system_prompt 是每次调用 think() 时动态生成的最终字符串，可能包含大量内容（用户问题、记忆、用户画像等）。
  3. 如果 system_prompt 很大且频繁生成，即使它是局部变量，在函数执行期间也会占用内存；函数结束后如果没有其他引用，才会被回收。

总结

  • self.prompt_template：持久存在（只要 agent 实例存在）。
  • system_prompt：函数结束后可能被回收，但每次调用都会创建新的字符串对象。

性能

List Tuple

1. 创建速度：Tuple 完胜

这是两者差距最悬殊的地方。在 Python 内部，创建一个 Tuple 比创建一个 List 快得多（通常快 3-5 倍）。

  • List：是一个动态数组，Python 需要向操作系统申请一块内存，并预留一定的空间以备后续 append（扩容）。
  • Tuple：是固定大小的。Python 会对其进行资源缓存（Resource Caching）。对于小尺寸的 Tuple，Python 会直接从空闲内存池中分配，而不需要频繁与操作系统交互。

结论：如果你在循环中频繁地创建短小的坐标点（例如每帧产生几百个 (x, y)），用 Tuple 能节省不少开销。

2. 迭代/遍历速度：Tuple 略快

当你使用 for x in data: 遍历数据时，Tuple 的表现通常比 List 快 5% - 10%。

这种差距来自于底层的指针跳转。由于 Tuple 的内存布局是连续且固定的，CPU 的一级缓存（L1 Cache）命中率会更高。但在处理普通的 CV 业务逻辑（比如几百个检测框）时，这种纳秒级的差异在肉眼和整体逻辑中基本可以忽略不计。

3. 内存占用：Tuple 更省

由于 List 需要存储额外的元数据（如当前容量、长度、扩容策略等），它消耗的内存总是比 Tuple 多。
